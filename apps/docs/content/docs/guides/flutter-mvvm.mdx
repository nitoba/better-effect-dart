---
title: Flutter MVVM
description: Conecte Effects a Commands e estado tipado sem transformar a biblioteca em um state manager
---

Flutter renderiza estado muito bem. O que ele não decide por você é quem possui um Runtime, como chamadas repetidas devem ser coordenadas ou como separar uma falha de domínio de um defect. `better_effect_flutter` cobre essa fronteira e deixa Provider, Riverpod, BLoC, Signals ou outra ferramenta continuarem responsáveis pela composição de UI.

O exemplo usa `Session`, `AuthFailure` e `signIn` do [guia de Effects](./effects).

## Fluxo da tela

```text
Widget
  ↓ intenção
ViewModel
  ↓
EffectCommand
  ↓ executa
Effect<Session, AuthFailure>
  ↓
Runtime
  ↓
EffectCommandState<Session, AuthFailure>
  ↓
Builder / Listener / Selector
```

O ViewModel não precisa possuir `AuthApi`, injector ou Runtime. Ele recebe a factory de Commands do subtree.

## 1. O ViewModel possui o Command

```dart
typedef LoginInput = ({String email, String password});

final class LoginViewModel extends EffectViewModel {
  LoginViewModel(super.commands) {
    login = commandWithInput<LoginInput, Session, AuthFailure>(
      (input) => signIn(input.email, input.password),
      policy: const CommandPolicy.drop(),
      keepPreviousData: false,
      debugLabel: 'LoginViewModel.login',
    );
  }

  late final EffectCommand<LoginInput, Session, AuthFailure> login;
}
```

`drop` é uma decisão da interação: enquanto uma submissão está ativa, um segundo caller compartilha a execução autoritativa em vez de iniciar outro login.

`EffectViewModel` não é obrigatório. Se o projeto já tem outra classe base, use `EffectCommandOwner` e registre os Commands que aquele owner deve descartar.

## 2. Crie o ViewModel no boundary Flutter

```dart
EffectViewModelBuilder<LoginViewModel>(
  create: (_, commands) => LoginViewModel(commands),
  builder: (_, viewModel, _) => LoginScreen(viewModel: viewModel),
)
```

`EffectViewModelBuilder` observa a factory scoped. Se um `BetterEffectFeatureScope` substituir o Runtime/Commands da feature, o ViewModel owned é recriado contra o novo ambiente.

Integrações com Provider/Riverpod/BLoC podem criar o mesmo ViewModel usando `context.effectCommands` no boundary de DI escolhido pela aplicação.

## 3. Renderize estado e trate side effects separadamente

```dart
final class LoginScreen extends StatelessWidget {
  const LoginScreen({required this.viewModel, super.key});

  final LoginViewModel viewModel;

  @override
  Widget build(BuildContext context) {
    return EffectCommandConsumer<Session, AuthFailure>(
      command: viewModel.login,
      onSuccess: (context, session) {
        Navigator.of(context).pushReplacementNamed('/home');
      },
      onFailure: (context, failure, previous) {
        ScaffoldMessenger.of(context).showSnackBar(
          SnackBar(content: Text(failure.toString())),
        );
      },
      onDefect: (context, defect, stackTrace, previous) {
        FlutterError.reportError(
          FlutterErrorDetails(
            exception: defect,
            stack: stackTrace,
          ),
        );
      },
      builder: (context, state, child) {
        return LoginForm(
          busy: state.isRunning,
          onSubmit: (input) => viewModel.login.execute(input),
        );
      },
    );
  }
}
```

`EffectCommandBuilder` é suficiente quando a View só renderiza estado. `EffectCommandListener` ou `EffectCommandConsumer` deve receber navegação, SnackBar, dialog e analytics.

Cada estado tem `revision`; listeners entregam cada revisão uma vez. Rebuild de widget não exige `clearError()` para evitar repetir uma navegação.

## 4. Trate os estados como uma união, não como booleans soltos

```dart
Widget loginBody(EffectCommandState<Session, AuthFailure> state) {
  return switch (state) {
    EffectCommandIdle() => const LoginPrompt(),
    EffectCommandRunning(:final previous) => LoginForm(
      busy: true,
      previousSession: previous,
    ),
    EffectCommandSuccess(:final value) => SessionView(value),
    EffectCommandFailure(:final error, :final previous) =>
      LoginError(error, previous),
    EffectCommandDefect(:final defect) => UnexpectedErrorView(defect),
    EffectCommandInterrupted(:final previous) => InterruptedView(previous),
  };
}
```

A diferença é útil: `AuthFailure` pode virar uma mensagem de produto; um defect deve normalmente ir para observabilidade; uma interruption representa perda de ownership da execução, não uma falha de domínio.

## 5. Isole rebuilds com seleção tipada

Quando um fragmento só depende de loading:

```dart
EffectCommandSelector<Session, AuthFailure, bool>(
  command: viewModel.login,
  selector: (state) => state.isRunning,
  builder: (context, running, child) {
    return LoginProgress(visible: running);
  },
)
```

Para fila, debounce e throttle, `EffectCommandSelector.snapshot` expõe `pendingCount`, `queuedCount` e `triggerPendingCount` sem fabricar novas revisões de UI. Veja [Seletores de Command](./command-selectors).

## 6. Inicie o Runtime no owner correto

Na raiz da aplicação:

```dart
Future<void> main() {
  return runBetterEffectApp(
    module: appModule,
    app: const App(),
  );
}
```

`runBetterEffectApp` inicia um Runtime e monta um `BetterEffectProvider` com ownership de aplicação.

Quando startup precisa aparecer como estado declarativo:

```dart
BetterEffectBootstrap(
  module: appModule,
  loadingBuilder: (_) => const SplashScreen(),
  errorBuilder: (context, error, stackTrace, retry) {
    return StartupError(error: error, onRetry: retry);
  },
  builder: (_) => const FeatureRoot(),
)
```

Quando outro boundary já possui o Runtime, use `BetterEffectProvider.value`. Essa variante representa ownership externo e não fecha o Runtime.

## 7. Escolha a policy pelo significado da ação

### Submit ou refresh: `drop`

```dart
submit = commandWithInput(
  submitOrder,
  policy: const CommandPolicy.drop(),
);
```

Uma nova chamada concorrente não duplica o trabalho autoritativo.

### Busca: `latest`

```dart
search = commandWithInput(
  searchProducts,
  policy: const CommandPolicy.latest(
    cancelPrevious: true,
  ),
);
```

Somente a chamada mais nova pode controlar o estado visível. Com `cancelPrevious: true`, a policy solicita interrupção cooperativa da execução anterior.

### Escritas ordenadas: `queue`

```dart
sync = commandWithInput(
  persistChange,
  policy: const CommandPolicy.queue(
    maxPending: 20,
    overflow: QueueOverflow.dropOldest,
  ),
);
```

Callers admitidos são processados em FIFO. Limite a fila quando entrada ilimitada seria um risco operacional.

`EffectCommandConcurrency.drop/latest/queue` continua disponível como shorthand de compatibilidade. Para código novo que precisa de cancelamento, trigger ou overflow, `CommandPolicy` comunica a decisão completa.

## 8. Debounce e throttle usam o clock do Runtime

```dart
search = commandWithInput(
  searchProducts,
  policy: const CommandPolicy.latest(
    trigger: TriggerPolicy.debounce(
      Duration(milliseconds: 300),
    ),
  ),
);
```

Triggers temporais são válidos para Commands com input e resolvem `EffectClock` no ambiente. O package não instala timer/clock global implicitamente.

Registre o clock onde a policy deve usá-lo:

```dart
final module = Module([
  .instance<EffectClock>(const SystemEffectClock()),
  // demais bindings...
]);
```

Veja [Políticas de Command](./command-policies) para leading/trailing, fila limitada, outcomes de callers e retry do último input aceito.

## 9. Cancelamento é cooperativo

`viewModel.login.cancel()` revoga a ownership lógica do Command e solicita interruption da execução gerenciada. O caller pode receber `ExitInterrupted` antes de o `Future` físico terminar.

Quando uma API externa suporta cancelamento, conecte-a ao sinal da execução **dentro do Effect**:

```dart
Effect<Response, RequestFailure> sendRequest() => Effect.result((use) async {
  final client = use<HttpClient>();

  return client.send(
    cancellation: use.cancellation.whenCancelled,
  );
});
```

Ou cruze um boundary cooperativo com `use.cancellation.throwIfCancelled()`.

Não trate `cancel()` como garantia de preempção de qualquer `Future` Dart. O Runtime mantém Scope e recursos até a conclusão física.

## 10. Feature Runtime quando o lifetime é menor que o app

Checkout, editor, área autenticada ou wizard podem compartilhar recursos entre várias telas sem promovê-los ao Runtime raiz:

```dart
BetterEffectFeatureScope(
  module: checkoutModule,
  label: 'checkout',
  loadingBuilder: (_) => const CheckoutLoading(),
  errorBuilder: (_, error, stackTrace, retry) {
    return CheckoutError(error: error, onRetry: retry);
  },
  builder: (_) => const CheckoutFlow(),
)
```

O scope cria um child Runtime com resolução local-first e fallback para o pai. Fechar a feature não fecha o Runtime da aplicação. Veja [Feature scopes](./feature-scopes).

## 11. Teste Runtime → Command → ViewModel sem rede global

```dart
final runtime = await appModule
    .overrideWith([
      .instance<AuthApi>(FakeAuthApi.success()),
    ])
    .start();

try {
  final viewModel = LoginViewModel(EffectCommands(runtime));

  try {
    final exit = await viewModel.login.execute((
      email: 'dev@example.com',
      password: 'secret',
    ));

    expect(exit, isA<ExitSuccess<Session, AuthFailure>>());
  } finally {
    viewModel.dispose();
  }
} finally {
  await runtime.close();
}
```

Para widget tests, use `BetterEffectProvider.value` ou `BetterEffectTestApp` quando o teste é o owner do Runtime.

## O que é recomendação e o que é regra

- **Regra da API:** Commands têm owner, Runtime tem owner e `Exit` distingue failure/defect/interruption.
- **Recomendação:** View fala com ViewModel em vez de resolver dependências de negócio diretamente.
- **Opcional:** usar `EffectViewModel`; `EffectCommandOwner` permite outra base.
- **Não é exigência:** um ViewModel por tela, um state manager específico ou uma arquitetura de pastas única.
