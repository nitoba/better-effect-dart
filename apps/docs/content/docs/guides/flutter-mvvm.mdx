title: "Flutter: integração completa"
description: Do Effect Dart ao widget, com Runtime, Commands, ViewModels e todos os boundaries Flutter
---

Uma aplicação Flutter com `better_effect` não possui uma arquitetura Dart e outra arquitetura Flutter. O fluxo é contínuo: domínio e infraestrutura produzem `Effect<A, E>` usando o core, o Runtime executa essa operação e `better_effect_flutter` transforma a execução em uma unidade que a árvore consegue possuir e observar.

Este guia mostra esse fluxo de ponta a ponta. Para uma referência de cada símbolo público, consulte o [mapa completo do package `better_effect_flutter`](../packages/better_effect_flutter).

## A arquitetura inteira em uma imagem mental

```text
DART / CORE

Module
  ↓ cria
Runtime
  ↓ executa
Effect<A, E>
  ├─ use<T>()
  ├─ resources / Scope
  ├─ retry / timeout / concurrency
  └─ RuntimeObserver
  ↓
Exit<A, E>

──────────────── boundary Flutter ────────────────

BetterEffectScope
  ↓ fornece
EffectCommands
  ↓ cria
EffectCommand<I, A, E>
  ↓ publica
EffectCommandState<A, E>
  ↓
ViewModel opcional
  ↓
Builder / Listener / Consumer / Selector
  ↓
Widget
```

O ponto central é: **o Command não substitui o Effect**. Ele executa o mesmo Effect que poderia ser usado em Dart puro, em testes, em um worker ou diretamente por `Runtime.run`.

## 1. Comece pelo domínio Dart

Considere um login. Nada nesta parte conhece Flutter:

```dart
sealed class AuthFailure implements Exception {
  const AuthFailure();
}

final class InvalidCredentials extends AuthFailure {
  const InvalidCredentials();
}

final class AuthUnavailable extends AuthFailure {
  const AuthUnavailable(this.cause);
  final Exception cause;
}

final class Session {
  const Session(this.userId);
  final String userId;
}

abstract interface class AuthRepository {
  Effect<Session, AuthFailure> signIn(String email, String password);
}

Effect<Session, AuthFailure> signIn(
  String email,
  String password,
) => Effect.result((use) async {
  final repository = use<AuthRepository>();
  return use.unwrap(repository.signIn(email, password));
});
```

O `Effect` pode usar `retry`, `Effect.forEach`, `runWith`, resources ou qualquer outra API do core. Ao chegar no Flutter, nenhuma dessas capacidades é perdida.

## 2. Componha o Module normalmente

```dart
final appModule = Module([
  .provide<AuthRepository>(AuthRepositoryLive.new),
]);
```

O Module continua sendo o composition root das dependências. Flutter não cria um segundo container.

## 3. Coloque o Runtime na árvore

Há quatro formas principais de estabelecer o Runtime Flutter. A escolha depende de **quem cria** e **quem possui** esse Runtime.

### Aplicação inteira: `runBetterEffectApp`

```dart
Future<void> main() {
  return runBetterEffectApp(
    module: appModule,
    app: const App(),
  );
}
```

É o caminho mais curto quando a app possui o Runtime raiz.

### Startup como estado visual: `BetterEffectBootstrap`

```dart
BetterEffectBootstrap(
  module: appModule,
  loadingBuilder: (_) => const SplashScreen(),
  errorBuilder: (context, error, stackTrace, retry) {
    return StartupError(
      error: error,
      onRetry: retry,
    );
  },
  builder: (_) => const AppShell(),
)
```

Prefira quando startup, retry e restart do Runtime fazem parte da UI. `restartKey` permite substituir intencionalmente o ambiente; `minimumLoadingDuration` pode manter uma tela de loading por uma duração mínima quando ela é usada.

### Runtime já criado e owned pelo widget: `BetterEffectProvider`

```dart
BetterEffectProvider(
  runtime: runtime,
  ownership: BetterEffectRuntimeOwnership.widget,
  lifecyclePolicy: const BetterEffectLifecyclePolicy.widget(),
  child: const FeatureRoot(),
)
```

### Runtime owned por outro boundary: `BetterEffectProvider.value`

```dart
BetterEffectProvider.value(
  runtime: runtime,
  child: const Preview(),
)
```

Essa variante nunca fecha o Runtime. O owner externo continua responsável pelo cleanup.

Todas essas opções terminam publicando um `BetterEffectScope` com o `Runtime` e um `EffectCommands` ligados a ele.

## 4. Entenda `BetterEffectScope`

`BetterEffectScope` é o `InheritedWidget` de infraestrutura da integração:

```text
BetterEffectScope
  ├─ runtime
  └─ commands
```

Normalmente ele é criado pelos widgets de bootstrap/provider, mas adapters customizados podem usar:

```dart
final scope = BetterEffectScope.of(context);
final runtime = scope.runtime;
final commands = scope.commands;
```

A extension de `BuildContext` oferece aliases mais ergonômicos, que veremos depois.

## 5. Crie o Command que representa a intenção da UI

Um ViewModel pode receber `EffectCommands` e criar Commands sem receber Runtime, Module ou repository:

```dart
typedef LoginInput = ({String email, String password});

final class LoginViewModel extends EffectViewModel {
  LoginViewModel(super.commands) {
    login = commandWithInput<LoginInput, Session, AuthFailure>(
      (input) => signIn(input.email, input.password),
      policy: const CommandPolicy.drop(),
      keepPreviousData: false,
      debugLabel: 'auth.login',
    );
  }

  late final EffectCommand<LoginInput, Session, AuthFailure> login;
}
```

`EffectViewModel` é uma conveniência, não uma regra arquitetural. O Command também pode ser criado diretamente:

```dart
final login = commands.withInput<LoginInput, Session, AuthFailure>(
  (input) => signIn(input.email, input.password),
);
```

Ou um ViewModel com outra classe base pode usar `EffectCommandOwner` para registrar Commands owned.

## 6. Crie o ViewModel no boundary certo

### `EffectViewModelBuilder`

```dart
EffectViewModelBuilder<LoginViewModel>(
  create: (_, commands) => LoginViewModel(commands),
  builder: (_, viewModel, child) {
    return LoginScreen(viewModel: viewModel);
  },
)
```

Esse widget resolve `EffectCommands` do scope atual, cria o ViewModel e observa seu `ChangeNotifier`.

Comportamentos importantes:

- o ViewModel é disposed por padrão;
- `disposeViewModel: false` transfere ownership para outro boundary;
- `recreateKey` força recriação explícita;
- se o Runtime efetivo do scope muda, o ViewModel owned é recriado contra o novo ambiente;
- a identidade da closure `create` não causa recriação a cada rebuild;
- `child` pode preservar uma subtree estática;
- `onCreated` observa a nova instância.

Se Provider, Riverpod, BLoC ou outro framework já cria seus ViewModels, use simplesmente:

```dart
final viewModel = LoginViewModel(context.effectCommands);
```

## 7. O Command produz uma união de estados

```text
EffectCommandIdle
EffectCommandRunning
EffectCommandSuccess<A>
EffectCommandFailure<E>
EffectCommandDefect
EffectCommandInterrupted
```

A UI não precisa coordenar `isLoading`, `error`, `data`, `cancelled` e `unexpectedError` como flags independentes.

```dart
Widget loginBody(EffectCommandState<Session, AuthFailure> state) {
  return switch (state) {
    EffectCommandIdle() => const LoginPrompt(),
    EffectCommandRunning(:final previous) => LoginForm(
      busy: true,
      previousSession: previous,
    ),
    EffectCommandSuccess(:final value) => SessionView(value),
    EffectCommandFailure(:final error, :final previous) =>
      LoginError(error, previous),
    EffectCommandDefect(:final defect) => UnexpectedErrorView(defect),
    EffectCommandInterrupted(:final previous) => InterruptedView(previous),
  };
}
```

`execute()` também devolve `Future<Exit<A, E>>`, então um caller imperativo observa o mesmo trabalho:

```dart
final exit = await viewModel.login.execute((
  email: email,
  password: password,
));
```

## 8. Escolha o widget de UI pelo tipo de reação

A biblioteca oferece quatro widgets de Command. Eles não são alternativas aleatórias; cada um atende uma responsabilidade diferente.

### Só renderizar: `EffectCommandBuilder`

```dart
EffectCommandBuilder<Session, AuthFailure>(
  command: viewModel.login,
  builder: (context, state, child) {
    return LoginForm(
      busy: state.isRunning,
      child: child,
    );
  },
  child: const LoginFields(),
)
```

Use `buildWhen` quando nem toda transição deve reconstruir o subtree:

```dart
buildWhen: (previous, current) =>
    previous.isRunning != current.isRunning,
```

### Só side effect one-shot: `EffectCommandListener`

```dart
EffectCommandListener<Session, AuthFailure>(
  command: viewModel.login,
  onSuccess: (context, session) {
    Navigator.of(context).pushReplacementNamed('/home');
  },
  onFailure: (context, failure, previous) {
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text(failure.toString())),
    );
  },
  onDefect: (context, defect, stackTrace, previous) {
    FlutterError.reportError(
      FlutterErrorDetails(exception: defect, stack: stackTrace),
    );
  },
  child: const LoginForm(),
)
```

`listenWhen` filtra transições. `fireImmediately` pode entregar o estado presente no mount. O dispatch é post-frame e cada `revision` é consumida uma vez.

### Render + side effect: `EffectCommandConsumer`

```dart
EffectCommandConsumer<Session, AuthFailure>(
  command: viewModel.login,
  listenWhen: (previous, current) => current.isTerminal,
  onSuccess: (context, session) => openHome(context),
  buildWhen: (previous, current) =>
      previous.isRunning != current.isRunning,
  builder: (context, state, child) {
    return LoginForm(
      busy: state.isRunning,
      child: child,
    );
  },
  child: const LoginFields(),
)
```

Internamente ele combina Listener e Builder. `listenWhen` e `buildWhen` são independentes.

### Só uma projeção: `EffectCommandSelector`

```dart
EffectCommandSelector<Session, AuthFailure, bool>(
  command: viewModel.login,
  selector: (state) => state.isRunning,
  builder: (context, running, child) {
    return LoginProgress(visible: running);
  },
)
```

Use `equals` quando `==` não for a igualdade adequada.

#### `EffectCommandSelector.snapshot`

Fila, pending e triggers podem mudar sem criar uma revisão visual. Para isso existe o snapshot:

```dart
EffectCommandSelector.snapshot(
  command: viewModel.save,
  selector: (snapshot) => (
    pending: snapshot.pendingCount,
    queued: snapshot.queuedCount,
    trigger: snapshot.triggerPendingCount,
  ),
  builder: (context, counts, child) {
    return QueueStatus(counts: counts);
  },
)
```

`EffectCommandSnapshot` também contém `state`, `lastExit` e `policy`.

## 9. `EffectCommandConsumer` não é obrigatório

Uma tela pode combinar os widgets conforme o desenho da UI:

```dart
EffectCommandListener<Session, AuthFailure>(
  command: viewModel.login,
  onSuccess: (context, session) => openHome(context),
  child: Column(
    children: [
      EffectCommandSelector<Session, AuthFailure, bool>(
        command: viewModel.login,
        selector: (state) => state.isRunning,
        builder: (_, running, __) => LoginProgress(visible: running),
      ),
      EffectCommandBuilder<Session, AuthFailure>(
        command: viewModel.login,
        builder: (_, state, __) => loginBody(state),
      ),
    ],
  ),
)
```

Essa composição é intencional: listener, render e selector têm ciclos diferentes.

## 10. Escolha uma policy pelo significado da interação

### Submit/refresh: `drop`

```dart
submit = commandWithInput(
  submitOrder,
  policy: const CommandPolicy.drop(),
);
```

Uma chamada concorrente não inicia duplicata.

### Busca: `latest`

```dart
search = commandWithInput(
  searchProducts,
  policy: const CommandPolicy.latest(
    cancelPrevious: true,
  ),
);
```

A chamada mais nova controla o estado visível. `cancelPrevious: true` solicita interrupção cooperativa do trabalho anterior.

### Escritas ordenadas: `queue`

```dart
sync = commandWithInput(
  persistChange,
  policy: const CommandPolicy.queue(
    maxPending: 20,
    overflow: QueueOverflow.dropOldest,
  ),
);
```

Callers aceitos são processados em FIFO.

### Debounce/throttle

```dart
search = commandWithInput(
  searchProducts,
  policy: const CommandPolicy.latest(
    trigger: TriggerPolicy.debounce(
      Duration(milliseconds: 300),
    ),
  ),
);
```

Policies temporais usam `EffectClock` do Runtime:

```dart
final module = Module([
  .instance<EffectClock>(const SystemEffectClock()),
  // demais bindings...
]);
```

Veja [Políticas de Command](./command-policies) para leading/trailing, overflow, caller outcomes e retry input.

## 11. Cancelamento continua sendo uma semântica do core

`viewModel.login.cancel()` publica interruption para o caller/Command, mas não força a interrupção física de qualquer `Future` Dart.

Quando a API externa é cancelável, conecte o `CancellationSignal` dentro do Effect:

```dart
Effect<Response, RequestFailure> sendRequest() => Effect.result((use) async {
  final client = use<HttpClient>();

  return client.send(
    cancellation: use.cancellation.whenCancelled,
  );
});
```

Ou use:

```dart
use.cancellation.throwIfCancelled();
```

O Runtime mantém ownership físico do Scope/resources até a conclusão real.

## 12. Um Runtime por feature quando o lifetime pedir

Use `BetterEffectFeatureScope` para checkout, editor, wizard, sessão autenticada ou outro subtree que compartilha resources:

```dart
BetterEffectFeatureScope(
  module: checkoutModule,
  label: 'checkout',
  restartKey: checkoutSessionId,
  loadingBuilder: (_) => const CheckoutLoading(),
  errorBuilder: (_, error, stackTrace, retry) {
    return CheckoutError(error: error, onRetry: retry);
  },
  builder: (_) => const CheckoutFlow(),
)
```

O widget cria `parentRuntime.fork(checkoutModule)`:

```text
checkout Effect
  ↓
checkout Runtime
  ↓ fallback
application Runtime
```

Os resources da feature sobrevivem a múltiplas telas/ViewModels e fecham no dispose/restart da feature. O Runtime pai continua ativo.

Quando esse feature Runtime substitui o Runtime efetivo do subtree, `EffectViewModelBuilder` recria ViewModels owned contra o novo `EffectCommands`.

## 13. Use as extensions do `BuildContext` nos boundaries corretos

### Factory de ViewModel

```dart
final vm = LoginViewModel(context.effectCommands);
```

Esse read não escuta mudanças do scope.

### Adapter que deve reagir ao scope

```dart
final commands = context.watchEffectCommands();
```

### Runtime direto

```dart
final runtime = context.effectRuntime;
```

Reserve para integration boundaries.

### Executar Effect sem Command

```dart
final result = await context.runEffect(loadConfiguration());
final exit = await context.runEffectExit(loadConfiguration());
```

Isso é útil quando a operação não precisa de estado Command observável.

### Resolver serviço no boundary

```dart
final router = context.readEffectService<AppRouter>();
```

Evite transformar isso em service locator dentro da lógica de widget. Business code deve continuar usando `use<T>()` no Effect.

## 14. Observabilidade atravessa core e Flutter

No Runtime:

```dart
final runtime = await appModule.start(
  observers: [AppRuntimeObserver()],
);
```

Nos Commands:

```dart
final commands = EffectCommands(
  runtime,
  observer: (transition) => logCommandTransition(transition),
  policyObserver: (event) => logPolicyDecision(event),
);
```

`EffectCommandTransition` observa mudanças visuais do Command. `EffectCommandPolicyObserver` observa decisões de coordenação. `RuntimeObserver` observa a execução física, DI, resources, retry e cleanup.

Eles são complementares.

## 15. Widget tests usam ownership externo

```dart
import 'package:better_effect_flutter/testing.dart';

final harness = await TestRuntime.start(
  testModule,
  registerCleanup: (cleanup) => addTearDown(cleanup),
);

await tester.pumpWidget(
  BetterEffectTestApp(
    runtime: harness.runtime,
    child: const LoginScreen(),
  ),
);
```

`BetterEffectTestApp` usa `BetterEffectProvider.value`, portanto o teste — não a árvore — continua owner do Runtime. Ele também adiciona `Directionality`; use `MaterialApp` como child quando a UI precisar de Material, navigator, theme ou localizations.

O entrypoint de testing também oferece probes de Command, listener e policy.

## 16. Qual peça entra em cada problema?

| Problema | API |
| --- | --- |
| iniciar app e Runtime | `runBetterEffectApp` |
| startup com loading/error/retry | `BetterEffectBootstrap` |
| publicar Runtime owned pelo widget | `BetterEffectProvider` |
| publicar Runtime externo | `BetterEffectProvider.value` |
| acessar Runtime/Commands no subtree | `BetterEffectScope` / context extensions |
| lifetime de feature | `BetterEffectFeatureScope` |
| criar Commands | `EffectCommands` |
| ViewModel opcional com ownership | `EffectViewModel` / `EffectCommandOwner` |
| criar/observar ViewModel | `EffectViewModelBuilder` |
| render state | `EffectCommandBuilder` |
| side effect one-shot | `EffectCommandListener` |
| render + side effect | `EffectCommandConsumer` |
| rebuild por projeção | `EffectCommandSelector` |
| pending/queue/trigger/lastExit | `EffectCommandSelector.snapshot` |
| widget test | `BetterEffectTestApp` |

## O que é regra e o que é escolha

- **Regra semântica:** Runtime e Commands precisam de owners claros.
- **Regra semântica:** failure, defect e interruption continuam outcomes diferentes.
- **Regra semântica:** cancelamento não significa preempção física geral de `Future`.
- **Convenção recomendada:** View conversa com ViewModel e Effects resolvem dependencies.
- **Opcional:** `EffectViewModel` e `EffectViewModelBuilder`.
- **Opcional:** um state manager externo.
- **Não é regra:** um ViewModel por tela.
- **Não é regra:** todo Effect precisa virar Command.
