O analyzer resolve dois problemas diferentes. Um `Effect` descartado pode ser detectado no arquivo em que foi escrito; um serviço ausente no `Module` raiz só pode ser confirmado depois que a composição do projeto é conhecida.

```text
Analysis Server plugin → feedback local durante edição/analyze
Graph checker           → roots, Modules, dependências e CI
```

A linha documentada aqui é `better_effect_analyzer 0.4.x`.

## Ative o plugin

No `analysis_options.yaml` raiz:

```yaml
include: package:flutter_lints/flutter.yaml

plugins:
  better_effect_analyzer:
    version: ^0.4.0
```

Depois de salvar, reinicie o Dart Analysis Server da IDE.

Ao ser habilitado, o plugin registra sete warnings de correção. As lints arquiteturais e de migração são opt-in.

## Warnings de correção

### `discarded_effect`

Effects são lazy. Criar um `Effect` e descartar o valor não inicia I/O:

```dart
repository.save(user); // warning
```

Componha ou execute a operação:

```dart
await use.unwrap(repository.save(user));
return repository.save(user);
await runtime.run(repository.save(user));
```

### `discarded_effect_execution`

`Runtime.execute` devolve um handle gerenciado. Se o código cria esse handle e perde a referência, o caller também perde a forma explícita de observar o `Exit`:

```dart
runtime.execute(syncOrders()); // warning
```

Observe ou retorne a execução:

```dart
final execution = runtime.execute(syncOrders());
final exit = await execution.exit;
```

### `runtime_started_without_close`

Um Runtime criado com `Module.start()` possui recursos e precisa de um owner:

```dart
final runtime = await appModule.start(); // warning se o fechamento não for verificável
```

O padrão local é:

```dart
final runtime = await appModule.start();
try {
  await runtime.run(program);
} finally {
  await runtime.close();
}
```

O mesmo diagnóstico também considera child Runtimes criados manualmente com `Runtime.fork`.

### `unawaited_effect_context_operation`

`use.unwrap`, `use.result`, `use.tryAsync` e `use.acquire` devolvem Futures. Ignorar o Future perde o valor e a propagação esperada:

```dart
use.unwrap(repository.save(user)); // warning
```

Use `await` ou devolva o Future conforme a assinatura do callback:

```dart
await use.unwrap(repository.save(user));
```

### `missing_binding_type_argument`

Constructor tear-offs são `Function`. Declare o contrato que o grafo deve enxergar:

```dart
final module = Module([
  .provide<Database>(DatabaseLive.new),
]);
```

Um `ServiceKey<T>` tipado também pode fornecer a restrição de inferência.

### `incompatible_provider`

A implementação, instância ou resource precisa satisfazer o contrato registrado:

```dart
Module([
  .provide<UserRepository>(AnalyticsService.new), // warning
]);
```

### `duplicate_service_binding`

A identidade de um binding é o tipo de serviço + `ServiceKey` opcional. Duplicar a mesma identidade no mesmo `Module` é inválido:

```dart
Module([
  .provide<Database>(SqliteDatabase.new),
  .provide<Database>(MemoryDatabase.new), // warning
]);
```

Quando duas implementações são intencionais, use keys diferentes.

## Lints opt-in

Ative somente as regras que representam o contrato arquitetural do projeto:

```yaml
plugins:
  better_effect_analyzer:
    version: ^0.4.0
    diagnostics:
      effect_command_not_owned: true
      closed_runtime_exposed: true
      module_root_not_complete: true
      repository_requests_repository: true
      viewmodel_requests_service: true
      widget_requests_business_dependency: true
      singleton_viewmodel: true
```

As quatro últimas reforçam a direção sugerida pelo package Flutter:

```text
Widget → ViewModel → Repository / UseCase → Service / Client
```

Isso é uma escolha de arquitetura. Uma equipe que usa boundaries diferentes não deve habilitar a lint apenas porque ela existe.

`effect_command_not_owned`, `closed_runtime_exposed` e `module_root_not_complete` ajudam a tornar lifecycle e composition roots mais explícitos durante adoção/migração.

## Quick fixes

O plugin registra transforms somente para casos locais em que consegue preservar a intenção com segurança. A linha atual inclui fixes para:

- observar ou retornar um `EffectExecution` descartado;
- envolver um Runtime local em `try/finally`;
- registrar ownership de um `EffectCommand`;
- transformar um root visível em `Module.complete`.

O analyzer não gera uma arquitetura inteira quando o ownership não pode ser inferido.

## Graph checker: a visão global

Adicione `better_effect_analyzer` a `dev_dependencies` e rode na raiz do projeto:

```bash
dart run better_effect_analyzer
```

O checker analisa composição que pode atravessar vários arquivos e valida:

- serviços ausentes em roots completos;
- ciclos de dependência;
- ciclos de composição de `Module`;
- `Module`s selecionados que não existem;
- providers duplicados ou incompatíveis depois de `merge`/`overrideWith`;
- ordem inválida de dependências entre resources;
- ownership/lifecycle coberto também por diagnósticos do plugin.

## Quando usar `Module.complete`

`Module.complete` marca estaticamente um composition root que deve fornecer todas as dependências alcançáveis:

```dart
final appModule = Module.complete([
  .provide<ApiClient>(ApiClientLive.new),
  .provide<UserRepository>(UserRepositoryLive.new),
]);
```

O marker não altera o comportamento do Runtime. Ele dá ao analyzer evidência explícita de que aquele grafo pretende ser completo.

Roots também podem ser selecionados na CLI:

```bash
dart run better_effect_analyzer \
  --module appModule \
  --module backgroundModule
```

## Overlays e child Runtimes

A análise distingue um root completo de um ambiente scoped. `runWith`, `runExitWith`, `executeWith`, `Runtime.fork` e `BetterEffectFeatureScope` podem depender de serviços fornecidos pelo ambiente pai.

O analyzer continua validando dentro do overlay:

- duplicatas;
- compatibilidade de providers;
- ciclos locais;
- ordem de resources.

Ele não exige que um child repita bindings que pertencem corretamente ao parent apenas para “fechar” o grafo local.

## Investigue o grafo

Inclua testes no índice:

```bash
dart run better_effect_analyzer --include-tests
```

Explique um Module:

```bash
dart run better_effect_analyzer --explain appModule
```

Descubra por que um serviço é necessário:

```bash
dart run better_effect_analyzer --why UserRepository
```

Procure declarações provadamente não alcançáveis a partir dos complete roots:

```bash
dart run better_effect_analyzer --unused
```

## Formatos para automação

Diagnósticos:

```bash
dart run better_effect_analyzer --format machine
dart run better_effect_analyzer --format json
dart run better_effect_analyzer --format sarif
```

Grafo:

```bash
dart run better_effect_analyzer --graph --format text
dart run better_effect_analyzer --graph --format json
dart run better_effect_analyzer --graph --format dot
dart run better_effect_analyzer --graph --format mermaid
```

Grave em arquivo com `--output`/`-o`. Consulte a versão pública do schema com:

```bash
dart run better_effect_analyzer --schema-version
```

Warnings são fatais por padrão no CLI. Para um pipeline que deliberadamente aceita warnings:

```bash
dart run better_effect_analyzer --no-fatal-warnings
```

## Um gate de CI razoável

O analyzer complementa, não substitui, o analyzer padrão do Dart/Flutter:

```bash
dart analyze --fatal-infos
dart run better_effect_analyzer
```

Em Flutter:

```bash
flutter analyze --fatal-infos
dart run better_effect_analyzer
```

O primeiro comando verifica a linguagem, lints e plugin. O segundo valida a composição completa que foi possível indexar.

## Supressões

Para uma exceção pontual, use a sintaxe normal de ignore do analyzer com o código emitido pelo diagnóstico.

Se uma lint arquitetural não representa a arquitetura do projeto inteiro, remova-a de `diagnostics` em vez de espalhar ignores. A configuração deve comunicar quais regras a equipe escolheu adotar.

## Troubleshooting

### O plugin não aparece na IDE

Confirme que `analysis_options.yaml` está na raiz, que `version` resolve, e reinicie o Analysis Server. Em desenvolvimento local, `path` do plugin deve ser absoluto.

### O Flutter reporta conflito de analyzer

A release `0.4.x` usa `analysis_server_plugin >=0.3.14 <0.3.18` e `analyzer ^12.1.0`. Verifique a versão fixada pelo SDK Flutter antes de alterar constraints.

### O graph checker acusa falta de binding em uma feature

Confirme que o boundary foi reconhecido como overlay/child Runtime. Uma feature pode depender legitimamente do parent. Não duplique um binding apenas para silenciar a ferramenta sem entender o ownership.

### O analyzer não reconhece composição muito dinâmica

A ferramenta é estática. Factories e composição construídas de forma opaca em runtime podem não ser prováveis a partir do source. Nesses casos, torne o composition root mais explícito ou selecione roots manualmente quando possível.

## Limitação importante

Ausência de diagnóstico não é prova de comportamento runtime para código que a análise estática não consegue modelar. As garantias de lifecycle/outcome da biblioteca continuam definidas pelo source, pelos testes e pelo [contrato semântico](/docs/semantics).
