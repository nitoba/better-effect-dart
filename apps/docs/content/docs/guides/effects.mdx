title: Efeitos e falhas tipadas

Uma operação de produção costuma combinar rede, cache, validação e outras dependências. `Effect<A, E>` é útil quando essas etapas precisam continuar lazy e componíveis sem transformar todo problema em uma exception genérica.

A ideia central é simples:

```text
Effect<A, E>
  ├─ sucesso esperado → A
  ├─ falha esperada   → E
  └─ evento inesperado → defect
```

## Um fluxo de login executável

O exemplo abaixo usa uma API em memória para continuar executável. A fronteira `AuthApi` pode depois receber uma implementação HTTP sem alterar o `Effect`.

```dart
import 'package:better_effect/better_effect.dart';

sealed class AuthFailure implements Exception {
  const AuthFailure();
}

final class InvalidCredentials extends AuthFailure {
  const InvalidCredentials();
}

final class AuthUnavailable extends AuthFailure {
  const AuthUnavailable(this.cause);
  final Exception cause;
}

final class InvalidCredentialsException implements Exception {
  const InvalidCredentialsException();
}

final class Session {
  const Session({required this.userId, required this.token});
  final String userId;
  final String token;
}

abstract interface class AuthApi {
  Future<Session> signIn(String email, String password);
}

final class DemoAuthApi implements AuthApi {
  @override
  Future<Session> signIn(String email, String password) async {
    if (password != 'secret') {
      throw const InvalidCredentialsException();
    }

    return Session(userId: email, token: 'demo-token');
  }
}

abstract interface class SessionCache {
  Future<void> write(Session session);
}

final class SessionCacheMemory implements SessionCache {
  Session? value;

  @override
  Future<void> write(Session session) async => value = session;
}

typedef AuthEffect<A extends Object> = Effect<A, AuthFailure>;

AuthEffect<Session> signIn(String email, String password) =>
    Effect.result((use) async {
      final api = use<AuthApi>();
      final cache = use<SessionCache>();

      final session = await use.tryAsync(
        () => api.signIn(email, password),
        onError: (error, stackTrace) => switch (error) {
          InvalidCredentialsException() => const InvalidCredentials(),
          _ => AuthUnavailable(error),
        },
      );

      await use.tryAsync(
        () => cache.write(session),
        onError: (error, stackTrace) => AuthUnavailable(error),
      );

      return session;
    });

final authModule = Module([
  .provide<AuthApi>(DemoAuthApi.new),
  .provide<SessionCache>(SessionCacheMemory.new),
]);
```

Agora a operação pode ser executada sem saber qual implementação concreta está por trás das interfaces:

```dart
final result = await authModule.run(
  signIn('dev@example.com', 'secret'),
);

result.fold(
  (session) => print('Sessão: ${session.userId}'),
  (failure) => print('Falha de login: $failure'),
);
```

Três decisões ficam explícitas:

1. `AuthFailure` contém condições que o caller pode tratar;
2. dependências são resolvidas durante a execução, não em um singleton global;
3. criar `signIn(...)` não chama API nem cache até um Runtime executá-lo.

## Escolha conscientemente a fronteira de exceptions

`Effect.tryAsync` e `use.tryAsync` capturam objetos que implementam `Exception` e os entregam ao `onError`.

`Error` e outros objetos lançados continuam sendo defects. Isso evita esconder um `StateError`, um bug de programação ou outro evento inesperado como “falha de login”.

Quando a aplicação realmente precisa mapear **qualquer** objeto lançado para `E`, use `Effect.tryAll` de forma explícita:

```dart
final parsed = Effect.tryAll<Data, ParseFailure>(
  decodePayload,
  onError: (error, stackTrace) => ParseFailure(error),
);
```

Essa escolha amplia a fronteira de captura; não é equivalente ao comportamento padrão de `tryAsync`.

## `run` para domínio, `runExit` para a borda completa

`Runtime.run`/`Module.run` devolvem `ResultDart<A, E>`. Defects permanecem visíveis como exceptions em vez de serem inventados dentro de `E`.

Quando uma borda precisa distinguir todos os outcomes como valor, use `runExit`:

```dart
final exit = await authModule.runExit(
  signIn('dev@example.com', 'secret'),
);

switch (exit) {
  case ExitSuccess(value: final session):
    print('Login: ${session.userId}');
  case ExitFailure(error: final failure):
    print('Falha esperada: $failure');
  case ExitDefect(defect: final defect, stackTrace: final stackTrace):
    print('Defect: $defect\n$stackTrace');
  case ExitInterrupted():
    print('Execução interrompida');
}
```

## Propague Effects e Results dentro de `Effect.result`

`EffectContext<E>` oferece operações que preservam a falha tipada do fluxo:

```dart
Effect<User, AppFailure> loadUser(String id) => Effect.result((use) async {
  final repository = use<UserRepository>();
  return use.unwrap(repository.find(id));
});
```

`use.unwrap` executa o Effect aninhado no mesmo contexto e propaga `E`. `use.result` faz o mesmo para um `ResultDart<A, E>` já existente.

Quando o fluxo precisa falhar diretamente:

```dart
return use.fail(const UserNotFound());
```

## Componha sem executar prematuramente

Operadores como `map`, `flatMap`, `mapError`, `catchAll`, `tap` e `zip` constroem outra descrição lazy:

```dart
final dashboard = Effect.zip(
  loadProfile(),
  loadNotifications(),
).map(
  (pair) => Dashboard(
    profile: pair.$1,
    notifications: pair.$2,
  ),
);
```

`Effect.zip` executa os lados em sequência. `Effect.parZip` inicia os dois; como Dart não fornece cancelamento físico geral para `Future`, se um lado terminar primeiro com falha/defect o outro ainda é aguardado antes de o Scope ser liberado.

Para coleções maiores, use [composição de coleções](./collection-composition) em vez de montar árvores de `parZip`.

## Resources não são apenas dependências

Uma conexão que pertence ao Runtime deve declarar aquisição e release juntos:

```dart
final module = Module([
  .resource<DatabaseConnection>(
    acquire: (_) => DatabaseConnection.open(),
    release: (connection, exit) => connection.close(),
  ),
  .provide<OrderRepository>(OrderRepositoryLive.new),
]);
```

O callback de release recebe o `Exit` que fechou o Scope. Resources do Module são adquiridos na ordem de declaração e fechados em ordem reversa.

Quando um recurso pertence somente à execução atual, use `use.acquire`:

```dart
final file = await use.acquire(
  openTemporaryFile(),
  release: (file, exit) => file.delete(),
);
```

Veja [recursos e ciclo de vida](./resources-and-lifetimes) para shutdown, cleanup failure e ownership físico após timeout/interruption.

## Contexto por execução sem global

`EffectLocal<T>` transporta contexto por execução:

```dart
const requestId = EffectLocal<String>('unknown', name: 'requestId');

final program = logRequest().withLocal(requestId, 'req-42');
await runtime.run(program);
```

Use `EffectLocal.metadata` quando o valor também deve aparecer em eventos de observabilidade. Não projete tokens, senhas ou payloads sensíveis como metadata.

## Quando não usar Effect

Não envolva toda função pura em `Effect`. Validações locais, formatadores e mapeamentos que não precisam de I/O, dependência contextual, falha tipada ou resource podem continuar como Dart comum.

A abstração é mais útil nas fronteiras em que a aplicação precisa responder com precisão **o que pode falhar, de que ambiente depende e quem possui os recursos usados pela operação**.
