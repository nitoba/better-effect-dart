Os packages oferecem entrypoints separados para código de teste:

```dart
import 'package:better_effect/testing.dart';
```

```dart
import 'package:better_effect_flutter/testing.dart';
```

Eles reexportam a API normal e acrescentam harnesses, gates determinísticos,
assertions tipadas e probes. O código de produção continua importando os
entrypoints principais.

## Um Runtime que pertence ao teste

`TestRuntime` inicia um Runtime real e conecta um
`RecordingRuntimeObserver`:

```dart
test('carrega o usuário configurado', () async {
  final harness = await TestRuntime.start(
    appModule.overrideWith([
      .instance<UserRepository>(FakeUserRepository.success(user)),
    ]),
    registerCleanup: (cleanup) => addTearDown(cleanup),
  );

  final exit = await harness.runExit(
    loadUser(user.id),
    executionLabel: 'users.load',
  );

  expect(exit, isExitSuccess<User, UserFailure>(user));
  harness.assertNoActiveExecutions();
});
```

O registrar de cleanup permite integrar o harness ao runner sem fazer o package
depender de `package:test`. Também é possível usar `try/finally` ou
`TestRuntime.use` para uma única operação.

## Verifique o canal correto do Exit

```dart
expect(exit, isExitSuccess<User, UserFailure>());
expect(exit, isExitFailure<User, UserFailure>(isA<UserNotFound>()));
expect(exit, isExitDefect<User, UserFailure>(isA<StateError>()));
expect(exit, isExitInterrupted<User, UserFailure>());
```

Quando o payload é necessário, use os extractors tipados:

```dart
final user = expectExitSuccess(exit);
final failure = expectExitFailure(exit);
final (:defect, :stackTrace) = expectExitDefect(exit);
expectExitInterrupted(exit);
```

Isso impede que uma falha esperada seja aceita como defeito ou que um bug passe
como erro de domínio.

## Controle concorrência sem sleeps

`TestGate<T>` libera uma operação com um valor conhecido:

```dart
final gate = TestGate<User>();

final execution = harness.execute(
  Effect.result((_) => gate.future),
);

// Faça assertions enquanto a execução está ativa.
gate.complete(user);
expect(await execution.exit, isExitSuccess<User, UserFailure>(user));
```

`TestSignal` serve para boundaries sem valor:

```dart
final started = TestSignal();
final continueWork = TestSignal();

final execution = harness.execute(
  Effect.result((_) async {
    started.signal();
    await continueWork.wait;
    return unit;
  }),
);

await started.wait;
continueWork.signal();
```

Use esses primitives para testar timeout, cancel-first, completion-first,
`latest`, fila e shutdown sem depender da velocidade da máquina.

## Verifique ordem de recursos

`TestEventRecorder<T>` mantém uma sequência imutável para aquisição e cleanup:

```dart
final events = TestEventRecorder<String>();

events.record('acquire:database');
events.record('acquire:transaction');
events.record('release:transaction');
events.record('release:database');

events.expectEvents([
  'acquire:database',
  'acquire:transaction',
  'release:transaction',
  'release:database',
]);
```

O Runtime recorder também permite aguardar eventos operacionais:

```dart
final ended = harness.observer.next<ExecutionEndEvent>(
  where: (event) => event.context.executionLabel == 'users.load',
);
```

`harness.assertNoActiveExecutions()` detecta Futures que ainda pertencem ao
Runtime depois que o teste observou um timeout ou uma interrupção lógica.

## Teste Commands sem montar widgets

```dart
final probe = EffectCommandProbe<User, UserFailure>(viewModel.loadUser);
addTearDown(probe.dispose);

final running = probe.waitFor<
  EffectCommandRunning<User, UserFailure>
>();
final success = probe.waitFor<
  EffectCommandSuccess<User, UserFailure>
>();

await viewModel.loadUser.execute(userId);

expect(await running, isA<EffectCommandRunning<User, UserFailure>>());
expect((await success).value.id, userId);
```

Para o estado atual, use extractors:

```dart
final user = expectCommandSuccess(command.value);
final failure = expectCommandFailure(command.value);
final (:defect, :stackTrace) = expectCommandDefect(command.value);

expectCommandIdle(command.value);
expectCommandRunning(command.value);
expectCommandInterrupted(command.value);
```

Uma sequência completa pode ser verificada por tipo:

```dart
probe.expectStateTypes([
  EffectCommandIdle<User, UserFailure>,
  EffectCommandRunning<User, UserFailure>,
  EffectCommandSuccess<User, UserFailure>,
]);
```

## Teste listeners one-shot

Use `EffectCommandListenerProbe` com o callback `onChanged`:

```dart
final listener = EffectCommandListenerProbe<User, UserFailure>();

EffectCommandListener(
  command: command,
  onChanged: listener.call,
  child: const UserScreen(),
);
```

Depois da interação:

```dart
expect(
  listener.deliveriesOf<EffectCommandFailure<User, UserFailure>>(),
  hasLength(1),
);
listener.expectUniqueRevisions();
```

Isso é útil para SnackBars, dialogs, navegação e analytics que não podem receber
a mesma revisão duas vezes.

## Widget tests com ownership externo

`BetterEffectTestApp` monta um `BetterEffectProvider.value` e adiciona
`Directionality`:

```dart
await tester.pumpWidget(
  BetterEffectTestApp(
    runtime: harness.runtime,
    child: const UserScreen(),
  ),
);
```

A árvore não fecha o Runtime. O teste continua owner por meio do `TestRuntime`.
Adicione um `MaterialApp` como child quando a tela precisar de tema,
localizations, navegação ou Scaffold.

## Valide um ResolverBackend customizado

Autores de backends podem executar o contrato compartilhado:

```dart
test('MyBackend respeita o contrato', () async {
  await runResolverBackendContractTests(
    createBackend: MyBackend.new,
  );
});
```

A suíte verifica lifetimes, keys, constructor injection, missing/circular
dependencies, duplicidade, idempotência, registration depois do commit, startup
parcial, fechamento, execução depois de close e overlays quando suportados.

Para inspecionar todos os resultados:

```dart
final report = await inspectResolverBackendContract(
  createBackend: MyBackend.new,
);

for (final failure in report.failures) {
  print('${failure.scenario.name}: ${failure.error}');
}
```

Containers que oferecem callbacks nativos de disposal podem fornecer uma
`ResolverBackendDisposalProbeFactory`. Sem essa probe, somente esse cenário
opcional aparece como skipped; falhas obrigatórias continuam falhando o report.

## Test doubles

O toolkit não implementa um framework de mocks. Prefira fakes pequenos e
`Module.overrideWith`:

```dart
final testModule = productionModule.overrideWith([
  .instance<Clock>(FakeClock.fixed(now)),
  .instance<UserRepository>(FakeUserRepository(users)),
]);
```

Assim o teste usa o mesmo Effect, Runtime, Scope e fluxo de cleanup da aplicação
real, substituindo apenas a borda de I/O.

## Checklist

- registre ou feche explicitamente todo `TestRuntime`;
- libere gates antes de encerrar o teste;
- use `assertNoActiveExecutions` para ownership físico;
- teste sucesso, falha tipada, defeito e interrupção quando forem relevantes;
- valide a política de concorrência escolhida pelo produto;
- dispose probes, ViewModels e Commands nos boundaries corretos;
- rode o TCK quando publicar um backend customizado;
- mantenha analyzer, graph checker, unit tests e widget tests como gates separados.
