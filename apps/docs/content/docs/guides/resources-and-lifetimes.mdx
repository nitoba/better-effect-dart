description: Escolha o owner correto para clients, conexões, subscriptions e recursos temporários

Uma dependência não é apenas um tipo. Ela também tem uma duração e um owner.
Um client HTTP pode viver durante toda a aplicação; uma transaction deve existir
somente durante uma operação. O package torna essa decisão explícita para que
aquisição e cleanup façam parte do mesmo desenho.

Os tipos usados nos exemplos representam adapters da aplicação. Eles aparecem
abreviados para manter o foco nas APIs públicas de lifecycle.

## Comece pela pergunta: quem é o dono?

| Recurso | Duração típica | Owner recomendado | API |
| --- | --- | --- | --- |
| Configuração e relógio | Runtime | Module raiz | `.provide` ou `.instance` |
| Client HTTP ou pool | Runtime | Module raiz | `.resource` |
| Contexto de request ou job | Uma execução | Module local | `runWith` / `executeWith` |
| Transaction compartilhada na operação | Uma execução | Module local | `.resource` no Module local |
| Arquivo temporário interno de uma função | Uma execução | Effect | `use.acquire` |
| Subscription de uma feature Flutter | Subtree | Runtime da feature | Provider/Bootstrap |

Se não está claro quem fecha o recurso, o desenho ainda está incompleto. Um
singleton global apenas esconde a pergunta até o shutdown.

## Recursos do Runtime com `Module.resource`

Use `Module.resource` quando a instância deve nascer junto com o Runtime e ser
reutilizada por várias operações:

```dart
abstract interface class ApiClient {
  Future<Response> get(Uri uri);
  Future<void> close();
}

final appModule = Module([
  .resource<ApiClient>(
    acquire: (_) async {
      final client = ApiClientHttp(
        baseUrl: Uri.parse('https://api.example.com'),
      );
      await client.connect();
      return client;
    },
    release: (client, exit) => client.close(),
  ),
  .provide<OrdersApi>(OrdersApiHttp.new),
]);
```

O callback de release recebe o `Exit` que fechou o Scope. Mesmo que o client não
precise dessa informação, mantenha o segundo parâmetro na assinatura.

Resources são adquiridos na ordem declarada e liberados em ordem inversa:

```text
acquire Config → acquire ApiClient → acquire Database
close Database → close ApiClient → close Config
```

Se o startup falhar, os resources já adquiridos também são fechados.

## Recursos internos com `use.acquire`

Use `use.acquire` quando somente o Effect atual precisa do recurso:

```dart
Effect<ExportResult, ExportFailure> exportOrders() =>
    Effect.result((use) async {
      final file = await use.acquire(
        Effect.tryAsync(
          TemporaryFile.create,
          onError: (error, stack) => ExportFailure.open(error),
        ),
        release: (file, exit) => file.delete(),
      );

      final repository = use<OrderRepository>();
      final orders = await use.unwrap(repository.loadOrders());
      await file.write(encodeOrders(orders));
      return uploadExport(file);
    });
```

O release é registrado no Scope da execução. Falha tipada, defeito, interrupção
e timeout não exigem blocos de cleanup duplicados em cada ramo.

## Recursos compartilhados por uma única execução

Quando várias camadas da mesma operação precisam de contexto ou de um recurso
temporário, use um Module por execução:

```dart
final requestModule = Module([
  .instance<RequestContext>(requestContext),
  .resource<Transaction>(
    acquire: (services) {
      return services<Database>().beginTransaction();
    },
    release: (transaction, exit) async {
      switch (exit) {
        case ExitSuccess():
          await transaction.commit();
        case _:
          await transaction.rollback();
      }
    },
  ),
]);

final exit = await runtime.runExitWith(
  requestModule,
  handleRequest,
  executionLabel: 'http.request',
);
```

O Module local pode usar serviços do Runtime raiz, mas suas instâncias e
resources pertencem somente àquela execução.

## Escolha entre os mecanismos

<Accordions>
  <Accordion title="O recurso deve ser compartilhado por toda a app">
    Registre-o como `.resource` no Module raiz. Um Runtime de longa duração
    possui a instância e a fecha no shutdown.
  </Accordion>
  <Accordion title="O recurso é usado apenas dentro de uma função">
    Adquira-o com `use.acquire`. Esse é o caminho mais simples quando não há
    outros providers temporários envolvidos.
  </Accordion>
  <Accordion title="Várias camadas precisam do mesmo contexto temporário">
    Crie um Module local e execute com `runWith`, `runExitWith` ou
    `executeWith`. Isso serve para request context, tenant, transaction e jobs.
  </Accordion>
  <Accordion title="O recurso é criado pelo teste">
    Prefira `.instance`, `overrideWith` ou um Module local de teste. Não altere
    singletons globais nem compartilhe estado entre testes concorrentes.
  </Accordion>
</Accordions>

## Lifetimes de bindings

```dart
final module = Module([
  .provide<Clock>(SystemClock.new), // lazySingleton por padrão
  .singleton<AppConfig>(AppConfig.load),
  .factory<RequestId>(RequestId.new),
  .instance<FeatureFlags>(flags),
]);
```

- `lazySingleton`: cria na primeira resolução e reutiliza no Runtime;
- `singleton`: cria durante o startup;
- `factory`: cria uma instância por resolução;
- `instance`: usa um objeto já criado pelo composition root.

`singleton` significa uma instância por Runtime, não uma instância global para o
processo.

## Timeout e interrupção preservam o owner

Dart Futures não são canceláveis de forma geral. Por isso, um timeout pode
entregar a falha lógica antes de o trabalho físico terminar. Da mesma forma,
`execution.interrupt()` publica `ExitInterrupted`, mas o Future pode continuar
até observar cancelamento cooperativo.

O Runtime mantém o Scope vivo até a conclusão física. Isso evita fechar uma
transaction, um arquivo ou uma subscription enquanto o código ainda pode estar
usando o recurso.

Conecte APIs canceláveis ao sinal da execução:

```dart
final response = await client.send(
  cancellation: use.cancellation.whenCancelled,
);
```

Ou cruze um boundary explícito:

```dart
use.cancellation.throwIfCancelled();
```

## Shutdown é parte do contrato

```dart
final runtime = await appModule.start();

try {
  await serve(runtime);
} finally {
  await runtime.close(
    gracePeriod: const Duration(seconds: 2),
    interruptAfterGracePeriod: true,
  );
}
```

O Runtime rejeita novas execuções, aguarda as já iniciadas, pode solicitar
interrupção cooperativa e só depois fecha resources e o resolver.

Falhas de cleanup são defeitos operacionais. Encaminhe-as para observabilidade
em vez de escondê-las:

```dart
final runtime = await appModule.start(
  observers: [AppObserver()],
);
```

## Flutter e ownership

No Flutter, escolha explicitamente quem é dono do Runtime:

- `BetterEffectRuntimeOwnership.application`: Runtime da aplicação;
- `BetterEffectRuntimeOwnership.widget`: Runtime de uma feature/subtree;
- `BetterEffectProvider.value`: Runtime externo, fechado por outro boundary.

Use `BetterEffectLifecyclePolicy` para configurar disposal, saída da aplicação,
grace period e interrupção cooperativa. A UI não deve fechar manualmente clients
que pertencem ao Runtime.
