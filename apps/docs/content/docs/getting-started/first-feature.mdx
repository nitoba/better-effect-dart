---
title: Sua primeira feature
description: Execute um fluxo completo com Effect, serviço, repository, Module e override de teste
---

O objetivo deste tutorial é chegar a um programa executável antes de introduzir detalhes avançados. A feature carrega pedidos, transforma exceptions de infraestrutura em uma falha de domínio e permite trocar a fonte de dados sem alterar a operação.

Ao final, o fluxo é:

```text
main/test
   ↓
loadOrders()
   ↓
OrderRepository
   ↓
OrdersApi
   ↓
Module escolhe a implementação
```

## 1. Crie um exemplo completo

Depois de instalar `better_effect`, coloque este código em `bin/main.dart` de um projeto Dart:

```dart
import 'package:better_effect/better_effect.dart';

sealed class OrderFailure implements Exception {
  const OrderFailure();
}

final class OrdersUnavailable extends OrderFailure {
  const OrdersUnavailable(this.cause);

  final Exception cause;

  @override
  String toString() => 'OrdersUnavailable($cause)';
}

final class Order {
  const Order({required this.id, required this.total});

  final String id;
  final double total;
}

abstract interface class OrdersApi {
  Future<List<Order>> getOrders();
}

final class DemoOrdersApi implements OrdersApi {
  @override
  Future<List<Order>> getOrders() async {
    return const [
      Order(id: 'ord-1', total: 42),
      Order(id: 'ord-2', total: 18),
    ];
  }
}

abstract interface class OrderRepository {
  Effect<List<Order>, OrderFailure> load();
}

final class OrderRepositoryLive implements OrderRepository {
  @override
  Effect<List<Order>, OrderFailure> load() => Effect.result((use) async {
    final api = use<OrdersApi>();

    return use.tryAsync(
      api.getOrders,
      onError: (error, stackTrace) => OrdersUnavailable(error),
    );
  });
}

final appModule = Module([
  .provide<OrdersApi>(DemoOrdersApi.new),
  .provide<OrderRepository>(OrderRepositoryLive.new),
]);

Effect<List<Order>, OrderFailure> loadOrders() => Effect.result((use) async {
  final repository = use<OrderRepository>();
  return use.unwrap(repository.load());
});

Future<void> main() async {
  final result = await appModule.run(loadOrders());

  result.fold(
    (orders) => print('Pedidos carregados: ${orders.length}'),
    (failure) => print('Falha: $failure'),
  );
}
```

Execute:

```bash
dart run bin/main.dart
```

Saída esperada:

```text
Pedidos carregados: 2
```

A chamada `loadOrders()` não executa a API. Ela cria um `Effect`. `appModule.run(...)` cria o Runtime, executa o Effect e fecha o Runtime quando a operação termina.

## 2. Entenda onde cada decisão ficou

`OrdersApi` representa a fronteira que pode falar HTTP, GraphQL, banco ou outra fonte. O exemplo usa `DemoOrdersApi` para continuar executável sem exigir uma biblioteca HTTP externa.

`OrderRepositoryLive` traduz a exception da API para `OrdersUnavailable`, que faz parte do contrato de `OrderFailure`. `use.tryAsync` captura `Exception`; `Error` e outros defects inesperados não são convertidos silenciosamente em falha de domínio.

`loadOrders()` resolve o repository somente quando o Effect está rodando. A operação não conhece `DemoOrdersApi` nem o container usado pelo Runtime.

`appModule` é o composition root: é ali que o contrato `OrdersApi` recebe uma implementação concreta.

## 3. Substitua a demo por I/O real no boundary

Em produção, `OrdersApi` pode encapsular `package:http`, Dio, gRPC ou outro client. Essa dependência externa pertence à implementação do adapter; o restante da feature pode manter os mesmos contratos:

```dart
final class HttpOrdersApi implements OrdersApi {
  HttpOrdersApi(this._client);

  final OrdersHttpClient _client;

  @override
  Future<List<Order>> getOrders() async {
    final response = await _client.get('/orders');
    return decodeOrders(response);
  }
}
```

O trecho acima é **pseudocódigo de integração**: `OrdersHttpClient` e `decodeOrders` representam o client/decoder escolhidos pela aplicação e não fazem parte de `better_effect`.

A composição de produção poderia registrar:

```dart
final productionModule = Module([
  .provide<OrdersHttpClient>(OrdersHttpClientLive.new),
  .provide<OrdersApi>(HttpOrdersApi.new),
  .provide<OrderRepository>(OrderRepositoryLive.new),
]);
```

Constructor injection funciona bem para dependências estruturais como o client usado por um adapter. `use<T>()` continua útil para dependências contextuais no ponto em que a operação precisa delas.

## 4. Separe arquivos quando a feature crescer

O exemplo cabe em um arquivo para facilitar o primeiro resultado. Em uma aplicação real, uma organização pequena pode ser suficiente:

<Files>
  <Folder name="lib" defaultOpen>
    <Folder name="orders" defaultOpen>
      <Folder name="domain" defaultOpen>
        <File name="order.dart" />
        <File name="order_failure.dart" />
      </Folder>
      <Folder name="data" defaultOpen>
        <File name="orders_api.dart" />
        <File name="order_repository.dart" />
        <File name="order_repository_live.dart" />
      </Folder>
      <File name="orders_module.dart" />
      <File name="load_orders.dart" />
    </Folder>
  </Folder>
</Files>

Essa árvore é uma sugestão, não uma exigência do package. O objetivo é preservar responsabilidades: domínio não precisa conhecer HTTP, adapters traduzem infraestrutura e o Module escolhe implementações.

## 5. Troque a folha no teste

O mesmo `Effect` pode rodar com outra implementação sem estado global. Adicione `test` como `dev_dependency` se o projeto ainda não usa o package:

```bash
dart pub add --dev test
```

Em `test/load_orders_test.dart`, importe o arquivo usado pelo primeiro exemplo:

```dart
import '../bin/main.dart';
import 'package:test/test.dart';

final class FakeOrdersApi implements OrdersApi {
  const FakeOrdersApi(this.orders);

  final List<Order> orders;

  @override
  Future<List<Order>> getOrders() async => orders;
}

test('carrega pedidos usando um override local', () async {
  final module = appModule.overrideWith([
    .instance<OrdersApi>(
      const FakeOrdersApi([
        Order(id: 'ord-test', total: 99),
      ]),
    ),
  ]);

  final result = await module.run(loadOrders());

  expect(result.isSuccess(), isTrue);
  expect(result.getOrThrow().single.id, 'ord-test');
});
```

Para código de produção, mova as APIs reutilizáveis para `lib/` e prefira um import `package:`. O import relativo acima existe apenas para manter o primeiro tutorial executável sem exigir que o leitor escolha antecipadamente o nome do próprio package.

O teste mantém `OrderRepositoryLive` e `loadOrders()`. Apenas a folha que representa I/O foi substituída.

## 6. Mantenha um Runtime quando houver um owner de vida longa

`Module.run` é ideal para uma operação curta porque cuida do Runtime automaticamente. Workers, servidores e outras aplicações com múltiplas execuções normalmente criam um Runtime uma vez:

```dart
Future<void> runWorker() async {
  final runtime = await appModule.start();

  try {
    await runtime.run(loadOrders());
    await runtime.run(syncOrders());
  } finally {
    await runtime.close();
  }
}
```

`syncOrders()` representa outra operação da aplicação. O ponto importante é o `finally`: o boundary que criou o Runtime é responsável por fechá-lo.

No Flutter, esse ownership normalmente é coordenado por `runBetterEffectApp`, `BetterEffectBootstrap`, `BetterEffectProvider` ou `BetterEffectFeatureScope` em vez de um `try/finally` dentro da View.

## 7. Leve a operação para Flutter quando necessário

A operação `loadOrders()` pode continuar no core Dart. No Flutter, um `EffectCommand` executa o mesmo Effect e projeta o `Exit` em estado observável:

```text
Effect<List<Order>, OrderFailure>
                 ↓
EffectCommand
                 ↓
Idle / Running / Success / Failure / Defect / Interrupted
```

O guia de [Flutter MVVM](../guides/flutter-mvvm) mostra como criar o Command, escolher a policy de chamadas repetidas e separar renderização de efeitos one-shot.

## O que este tutorial garantiu

- o exemplo inicial usa somente APIs públicas da linha `0.4.x`;
- o primeiro bloco é executável sem dependência HTTP externa;
- o trecho de integração HTTP está explicitamente marcado como pseudocódigo;
- a falha de domínio é diferente de um defect;
- o `Module` escolhe implementações sem expor um injector global à operação;
- o teste troca um binding sem alterar o Effect;
- o Runtime tem um owner responsável pelo fechamento.
