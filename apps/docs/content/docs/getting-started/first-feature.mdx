---
title: Sua primeira feature
description: Construa uma leitura de pedidos com domínio, repository, Module e teste isolado
---

Este tutorial monta uma feature de ponta a ponta. O objetivo não é criar mais
classes por hábito: é mostrar onde cada decisão mora quando uma operação tem
I/O, uma falha que o produto conhece, uma implementação de produção e uma
implementação de teste.

Ao final, o fluxo será:

```text
UI / job → loadOrders() → OrderRepository → OrdersApi → HTTP
                  ↑             ↑               ↑
                Effect        Module          implementação live/fake
```

## 1. Separe o código pela responsabilidade

Uma organização pequena já comunica a arquitetura para quem entrar no projeto:

<Files>
  <Folder name="lib" defaultOpen>
    <Folder name="domain" defaultOpen>
      <File name="order.dart" />
      <File name="order_failure.dart" />
    </Folder>
    <Folder name="data" defaultOpen>
      <File name="orders_api.dart" />
      <File name="order_repository.dart" />
      <File name="order_repository_live.dart" />
    </Folder>
    <Folder name="config" defaultOpen>
      <File name="app_module.dart" />
    </Folder>
  </Folder>
  <Folder name="test">
    <File name="order_repository_test.dart" />
  </Folder>
</Files>

`domain` não sabe que existe HTTP. `data` traduz a infraestrutura para o
contrato do domínio. `config` escolhe implementações. A UI ou um worker apenas
executa a operação.

## 2. Modele o resultado que o produto entende

Não use uma exceção genérica para representar todos os motivos de a lista não
estar disponível:

```dart
sealed class OrderFailure implements Exception {
  const OrderFailure();
}

final class OrdersOffline extends OrderFailure {
  const OrdersOffline(this.cause);
  final Object cause;
}

final class OrdersUnauthorized extends OrderFailure {
  const OrdersUnauthorized();
}

final class OrdersInvalidResponse extends OrderFailure {
  const OrdersInvalidResponse(this.message);
  final String message;
}

final class Order {
  const Order({required this.id, required this.total});

  final String id;
  final double total;
}
```

Uma tela pode mostrar login quando recebe `OrdersUnauthorized`, oferecer retry
para `OrdersOffline` e enviar `OrdersInvalidResponse` para observabilidade.
Essa decisão fica possível porque a falha é parte do tipo da operação.

## 3. Defina portas, não implemente detalhes no domínio

O domínio precisa de uma capacidade pequena. A implementação live pode trocar
HTTP por GraphQL sem mudar o contrato:

```dart
abstract interface class OrdersApi {
  Future<List<Order>> getOrders();
}

abstract interface class OrderRepository {
  Effect<List<Order>, OrderFailure> loadOrders();
}
```

## 4. Adapte a API em um Effect

```dart
final class OrderRepositoryLive implements OrderRepository {
  const OrderRepositoryLive();

  @override
  Effect<List<Order>, OrderFailure> loadOrders() =>
      Effect.result((use) async {
        final api = use<OrdersApi>();

        return use.unwrap(
          Effect.tryAsync(
            api.getOrders,
            onError: (error, stack) => OrdersOffline(error),
          ),
        );
      });
}

Effect<List<Order>, OrderFailure> loadOrders() =>
    Effect.result((use) async {
      final repository = use<OrderRepository>();
      return use.unwrap(repository.loadOrders());
    });
```

O `Effect` é lazy: chamar `loadOrders()` descreve a operação, mas não abre a
rede. O I/O só acontece quando um `Runtime` executa a descrição. Isso permite
que a mesma feature seja montada em produção, preview e teste.

Se o seu repository já for a fronteira pública da feature, uma função factory
também pode resolver o serviço diretamente:

```dart
Effect<List<Order>, OrderFailure> loadOrders() => Effect.result((use) async {
  final repository = use<OrderRepository>();
  return use.unwrap(repository.loadOrders());
});
```

Escolha uma forma e mantenha a direção: o domínio pede uma porta; o Module
fornece uma implementação.

## 5. Componha o Module no composition root

```dart
final appModule = Module([
  .provide<OrdersApi>(OrdersApiHttp.new),
  .provide<OrderRepository>(OrderRepositoryLive.new),
]);
```

O tipo explícito em `.provide<T>` é importante. Ele documenta o contrato que
os consumidores podem resolver e permite ao analyzer verificar a composição.
O default `lazySingleton` evita criar clients que a execução não usa; escolha
`.singleton` quando a inicialização precisa acontecer no startup ou
`.factory` quando cada resolução deve ser independente.

## 6. Execute uma vez ou mantenha um Runtime

Para um comando ou script de curta duração, `Module.run` inicia e fecha os
recursos automaticamente:

```dart
Future<void> main() async {
  final result = await appModule.run(loadOrders());

  result.fold(
    (orders) => print('Pedidos: ${orders.length}'),
    (failure) => print('Falha: $failure'),
  );
}
```

Em uma aplicação, mantenha um Runtime durante a vida do owner:

```dart
Future<void> runWorker() async {
  final runtime = await appModule.start();

  try {
    await runtime.run(loadOrders());
    await runtime.run(syncOrders());
  } finally {
    await runtime.close();
  }
}
```

O `finally` não é detalhe cosmético: é onde o owner devolve conexões,
subscriptions e clients que pertencem ao Runtime. No Flutter, o owner costuma
ser `BetterEffectProvider` ou `BetterEffectBootstrap`.

## 7. Troque somente a implementação no teste

```dart
import 'package:test/test.dart';

final class FakeOrdersApi implements OrdersApi {
  const FakeOrdersApi(this.value);
  final List<Order> value;

  @override
  Future<List<Order>> getOrders() async => value;
}

test('carrega pedidos sem rede', () async {
  final module = appModule.overrideWith([
    .instance<OrdersApi>(
      FakeOrdersApi([const Order(id: 'ord-1', total: 42)]),
    ),
  ]);

  final result = await module.run(loadOrders());

  expect(result.getOrNull()?.single.id, 'ord-1');
});
```

O teste usa o mesmo `Effect`, o mesmo repository e a mesma composição; só a
folha que fala com a rede foi substituída. Não há singleton global para
resetar, `sleep` para esperar callback ou endpoint de staging para manter vivo.

## 8. Leve a operação para o Flutter quando fizer sentido

A tela não precisa conhecer `OrdersApi` nem criar `Runtime`. O guia de
[Flutter MVVM](../guides/flutter-mvvm) mostra como transformar `loadOrders()` em
um `EffectCommand`, escolher `drop`, `latest` ou `queue` e renderizar loading,
sucesso, falha e defeito sem callbacks espalhados.

## O que você construiu

| Peça | Responsabilidade |
| --- | --- |
| `OrderFailure` | Contrato de falhas esperadas |
| `OrderRepository` | Porta usada pelo domínio |
| `OrderRepositoryLive` | Adaptação de I/O para `Effect` |
| `appModule` | Composição das implementações |
| `Runtime` | Execução e ownership de recursos |
| `overrideWith` | Teste/preview sem alterar produção |

Esse é o menor fluxo que demonstra o poder real do package: a feature tem
semântica de erro, dependências substituíveis e ciclo de vida explícito sem
exigir uma camada mágica entre o Dart que você já escreve e o runtime.
