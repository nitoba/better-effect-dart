## Para que serve

`better_effect` é a camada de runtime da família. Ele combina:

- `Effect<A, E>` para operações lazy com falha tipada;
- `Effect.all` e `Effect.forEach` para coleções ordenadas com concorrência limitada;
- `Effect.retry` para falhas tipadas com policies e um Scope por tentativa;
- `Module` para declarar serviços, lifetimes e resources;
- `Runtime` e `Scope` para controlar execução e ciclo de vida;
- `Runtime.fork` para ambientes de feature com fallback para um Runtime pai;
- `EffectExecution` para interrupção cooperativa e ownership físico;
- `EffectLocal` para contexto por execução;
- `RuntimeObserver` para logs, métricas, tracing e diagnóstico operacional.

O core é Dart-only. Ele não importa Flutter, não impõe um state manager e não
cria um service locator global. Pode ser usado em packages de domínio, CLI,
backend Dart, workers e na camada compartilhada de uma aplicação Flutter.

## Primeiro Effect

```dart
import 'package:better_effect/better_effect.dart';

sealed class AppFailure implements Exception {
  const AppFailure();
}

final class NetworkFailure extends AppFailure {
  const NetworkFailure(this.message);
  final String message;
}

abstract interface class GreetingApi {
  Future<String> fetchGreeting();
}

final class GreetingApiLive implements GreetingApi {
  @override
  Future<String> fetchGreeting() async => 'Olá, better_effect';
}

Effect<String, AppFailure> loadGreeting() =>
    Effect.result((use) async {
      final api = use<GreetingApi>();
      return use.tryAsync(
        api.fetchGreeting,
        onError: (error, stack) => NetworkFailure(error.toString()),
      );
    });
```

Construir o Effect não executa I/O. A operação começa somente quando um Runtime
a executa.

## Componha coleções com um limite explícito

```dart
final users = Effect.forEach(
  userIds,
  loadUser,
  concurrency: 4,
);
```

O padrão é sequencial (`concurrency: 1`). O Runtime inicia os itens em ordem
FIFO, nunca ultrapassa o limite informado e devolve uma lista não modificável na
ordem da entrada, mesmo quando os Futures terminam fora de ordem.

Para uma coleção que já contém Effects:

```dart
final dashboard = Effect.all(
  [loadProfile(), loadNotifications(), loadPreferences()],
  concurrency: 3,
);
```

Fan-out sem limite precisa ser escolhido explicitamente com
`Effect.forEachUnbounded` ou `Effect.allUnbounded`. Depois de falha, defect ou
interrupção, nenhum item novo começa; os itens já iniciados continuam pertencendo
à execução até a conclusão física.

## Repita apenas falhas tipadas

```dart
final resilient = loadGreeting().retry(
  RetryPolicy.exponential(
    maxAttempts: 4,
    initialDelay: const Duration(milliseconds: 200),
    maxDelay: const Duration(seconds: 3),
  ),
);
```

A execução inicial conta como tentativa um. Cada tentativa recebe um
Scope filho, e seus resources fecham antes do delay ou da próxima
tentativa. Defects não são repetidos. Delays e jitter usam
`EffectClock` e `EffectRandom` registrados explicitamente; o Runtime não
instala serviços globais.

## Module e Runtime

```dart
final module = Module([
  .provide<GreetingApi>(GreetingApiLive.new),
]);

final runtime = await module.start();

try {
  final result = await runtime.run(loadGreeting());
  // Trate Success ou Failure.
} finally {
  await runtime.close();
}
```

Para uma operação única, use `module.run(effect)` ou `module.runExit(effect)`.
Essas APIs iniciam e fecham o Runtime automaticamente.

## Resources com owner explícito

Um resource do Module vive durante o Runtime:

```dart
final module = Module([
  .resource<ApiClient>(
    acquire: (_) => ApiClient.connect(),
    release: (client, exit) => client.close(),
  ),
]);
```

Um resource adquirido com `use.acquire` vive durante uma execução:

```dart
final file = await use.acquire(
  Effect.tryAsync(
    TemporaryFile.create,
    onError: TemporaryFileFailure.from,
  ),
  release: (file, exit) => file.delete(),
);
```

O callback de release recebe o `Exit` responsável pelo fechamento.

## Contexto e resources por execução

Use um Module local quando uma operação precisa de request context, tenant,
transaction ou overrides temporários:

```dart
final requestModule = Module([
  .instance<RequestContext>(requestContext),
  .resource<Transaction>(
    acquire: (services) {
      return services<Database>().beginTransaction();
    },
    release: (transaction, exit) => transaction.close(exit),
  ),
]);

final exit = await runtime.runExitWith(
  requestModule,
  handleRequest,
  executionLabel: 'http.request',
);
```

O ambiente local resolve seus próprios bindings primeiro e usa o Runtime raiz
como fallback. Nada é registrado globalmente.

## Child Runtimes para features

Quando o lifetime precisa durar mais que uma execução, mas menos que a aplicação,
crie um Runtime filho:

```dart
final checkoutRuntime = await runtime.fork(
  checkoutModule,
  label: 'checkout',
);

try {
  await checkoutRuntime.run(loadCheckout);
  await checkoutRuntime.run(validateCheckout);
} finally {
  await checkoutRuntime.close();
}
```

Bindings do filho têm precedência e serviços ausentes usam o Runtime pai como
fallback. Resources do Module da feature sobrevivem às duas execuções acima e
fecham quando `checkoutRuntime` fecha.

Fechar o filho nunca fecha o pai. Fechar o pai coordena seus filhos antes de
liberar resources parentais. `runWith` dentro de um child Runtime cria uma camada
ainda mais curta sem perder a cadeia de fallback.

Consulte [Feature scopes](../guides/feature-scopes) para o equivalente Flutter.

## Execuções gerenciadas

```dart
final execution = runtime.execute(
  synchronizeOrders(),
  label: 'orders.synchronize',
);

execution.interrupt(reason: 'screen-disposed');
final exit = await execution.exit;
```

A interrupção é cooperativa. O `ExitInterrupted` pode ser publicado antes da
conclusão física, mas o Runtime continua sendo owner do Scope e dos resources
até o Future terminar.

## Observabilidade

```dart
final runtime = await module.start(
  observers: [AppObserver()],
);
```

Observers podem acompanhar execuções, resolução de dependências, aquisição,
release, interrupção e falhas de cleanup. As falhas do próprio observer são
isoladas e não alteram o resultado dos Effects.

Em child Runtimes, `RuntimeEventContext` também identifica o Runtime owner, o
Runtime pai e a label da feature por `runtimeId`, `parentRuntimeId` e
`runtimeLabel`.

Use `EffectLocal.metadata` para request IDs, trace IDs e outros campos seguros:

```dart
const requestId = EffectLocal<String>.metadata(
  'unknown',
  name: 'request.id',
);

final program = loadUser.withLocals([
  requestId.bind('req-123'),
]);
```

## Composição de produção, teste e preview

Modules são descrições imutáveis. O mesmo grafo pode receber overrides sem
alterar a implementação:

```dart
final production = Module([
  .provide<Clock>(SystemClock.new),
  .provide<UserRepository>(UserRepositoryLive.new),
]);

final test = production.overrideWith([
  .instance<Clock>(FakeClock.fixed(DateTime(2026, 1, 1))),
  .instance<UserRepository>(FakeUserRepository()),
]);
```

Esse padrão evita estado global e permite Runtimes concorrentes com ambientes
diferentes.
