`better_effect` é o core Dart da família. Ele descreve operações lazy com `Effect<A, E>`, materializa dependências com `Module`/`Runtime` e mantém resources associados ao owner correto por meio de `Scope`.

Use o package em código Dart que precisa combinar I/O, falhas esperadas, dependências substituíveis e lifecycle explícito. Não há dependência de Flutter.

## O core continua sendo o runtime de uma aplicação Flutter

`better_effect_flutter` não substitui estas APIs. Ele depende deste package e reexporta sua superfície pública. Em uma aplicação Flutter, repositories, services, use cases e Effects continuam usando `Effect`, `Module`, `Runtime`, `Scope`, `Exit`, retry, concorrência, resources e observabilidade exatamente como em qualquer outro programa Dart.

A camada Flutter entra **depois**, quando uma execução precisa ser possuída pela árvore ou projetada em estado visual:

```text
better_effect
Module → Runtime → Effect<A, E> → Exit<A, E>
                    │
                    │ executado por
                    ▼
better_effect_flutter
EffectCommand → EffectCommandState → Widget
```

Por isso, ao estudar uma aplicação Flutter com esta família, não trate as páginas do core como documentação “somente para Dart puro”. Elas documentam o runtime que está por baixo dos Commands Flutter.

Veja o [mapa dos packages](/docs/packages) para a relação completa ou avance para [`better_effect_flutter`](/docs/packages/better_effect_flutter) quando já dominar `Effect`, `Module` e `Runtime`.

## API pública em um mapa

| Área | APIs principais | Para quê |
| --- | --- | --- |
| descrição de operação | `Effect<A, E>`, `EffectContext<E>` | sucesso/falha tipada, composição e acesso contextual |
| outcomes | `ExitSuccess`, `ExitFailure`, `ExitDefect`, `ExitInterrupted` | preservar o resultado completo de uma execução |
| DI | `Module`, `Binding`, `Lifetime`, `ServiceKey`, `Services` | declarar e resolver o ambiente |
| runtime | `Runtime`, `EffectExecution`, `CancellationSignal` | executar, acompanhar, interromper e fechar trabalho |
| resources | `Scope`, `EffectContext.acquire` | ownership e finalizers por runtime/execução |
| contexto local | `EffectLocal`, `EffectLocalBinding` | valores contextuais por execução e metadata |
| resiliência | `RetryPolicy`, `EffectClock`, `EffectRandom` | retry determinístico e testável |
| observabilidade | `RuntimeObserver` e eventos | logs, métricas, tracing e diagnóstico |
| testing | `package:better_effect/testing.dart` | runtime/clock/observer/matchers para testes |

O arquivo `better_effect.dart` também reexporta `result_dart`.

## Primeiro programa

```dart
import 'package:better_effect/better_effect.dart';

sealed class AppFailure implements Exception {
  const AppFailure();
}

final class LoadFailure extends AppFailure {
  const LoadFailure(this.cause);
  final Exception cause;
}

abstract interface class MessageSource {
  Future<String> load();
}

final class MemoryMessageSource implements MessageSource {
  @override
  Future<String> load() async => 'Olá, better_effect';
}

final module = Module([
  .provide<MessageSource>(MemoryMessageSource.new),
]);

Effect<String, AppFailure> loadMessage() => Effect.result((use) async {
  final source = use<MessageSource>();
  return use.tryAsync(
    source.load,
    onError: (error, stackTrace) => LoadFailure(error),
  );
});

Future<void> main() async {
  final result = await module.run(loadMessage());
  result.fold(print, print);
}
```

A chamada `loadMessage()` apenas cria a descrição. O I/O começa quando `Module.run` cria um Runtime e executa o Effect.

## Effect e fronteiras de erro

Dentro de `Effect.result`, o parâmetro `use` é um `EffectContext<E>` read-only. Ele pode resolver serviços, compor `Effect`/`ResultDart`, falhar com `use.fail`, ler locals e adquirir resources.

```dart
Effect<User, AppFailure> loadUser(String id) => Effect.result((use) async {
  final users = use<UserRepository>();
  final user = await use.unwrap(users.find(id));
  return user;
});
```

`use.unwrap` propaga uma falha tipada do Effect aninhado. `use.result` faz o mesmo para `ResultDart`.

Escolha a fronteira de exception de forma deliberada:

- `Effect.tryAsync` e `use.tryAsync` capturam `Exception`;
- `Error` e outros objetos lançados permanecem defects;
- `Effect.tryAll` captura qualquer objeto lançado e só deve ser usado quando isso é intencional;
- `Effect.sync` é lazy, mas exceptions lançadas pelo callback continuam sendo defects.

## Module, bindings e lifetimes

`Module` é uma descrição imutável. Construir um Module não instancia serviços nem adquire resources.

```dart
final appModule = Module([
  .instance(const AppConfig()),
  .provide<HttpClient>(HttpClientLive.new),
  .factory<CreateOrder>(CreateOrder.new),
]);
```

Bindings disponíveis:

| Binding | Lifetime |
| --- | --- |
| `.provide<T>(Constructor.new)` | `lazySingleton` por padrão |
| `.factory<T>(Constructor.new)` | uma instância por resolução |
| `.singleton<T>(Constructor.new)` | criada no startup |
| `.lazySingleton<T>(Constructor.new)` | criada na primeira resolução |
| `.instance<T>(value)` | valor já criado |
| `.resource<T>(...)` | adquirido no startup e liberado no shutdown |

`ServiceKey<T>` diferencia múltiplas implementações do mesmo contrato. Bindings com a mesma identidade de tipo + key são rejeitados.

## Scope e resources

Resources do `Module` pertencem ao Runtime. Resources de uma única execução pertencem ao Scope dessa execução:

```dart
final connection = await use.acquire(
  Effect.tryAsync(
    DatabaseConnection.open,
    onError: DatabaseFailure.from,
  ),
  release: (connection, exit) => connection.close(),
);
```

Child scopes fecham antes do pai. Finalizers são executados em ordem reversa de registro e o fechamento continua tentando os demais finalizers quando um release falha.

## Runtime e ownership físico

Para uma operação curta, prefira `module.run`/`runExit`. Para um processo de vida longa:

```dart
final runtime = await appModule.start();
try {
  await runtime.run(sync());
} finally {
  await runtime.close();
}
```

`Runtime.run` devolve `ResultDart` e repropaga defects. `runExit` preserva o outcome completo em `Exit`.

`Runtime.execute` cria um `EffectExecution` gerenciado. Interrupção é cooperativa: o caller pode receber `ExitInterrupted` antes do `Future` físico terminar, mas o Runtime continua possuindo o Scope e os resources até a conclusão real.

Essa regra também vale para `Effect.timeout` e continua valendo quando o Effect é executado por um `EffectCommand` Flutter.

## Coleções e concorrência

```dart
final users = Effect.forEach(
  userIds,
  loadUser,
  concurrency: 4,
);
```

`all`/`forEach` são sequenciais por padrão. Com concorrência limitada, o scheduler inicia trabalho em FIFO, preserva a ordem da lista de saída e deixa de iniciar novos itens depois de falha, defect ou interruption. Trabalho já iniciado ainda é aguardado.

Use `allUnbounded`/`forEachUnbounded` somente quando fan-out sem limite for desejado explicitamente.

## Retry

```dart
final resilient = request().retry(
  RetryPolicy.exponential(
    maxAttempts: 4,
    initialDelay: const Duration(milliseconds: 200),
    maxDelay: const Duration(seconds: 3),
  ),
);
```

Retry considera apenas o canal de falha tipado. Cada tentativa recebe um child `Scope` novo, fechado antes de avaliar policy, dormir ou iniciar a próxima tentativa.

Policies com delay resolvem `EffectClock`; jitter resolve `EffectRandom`. Nenhum dos dois é instalado implicitamente.

O mesmo retry pode ser usado em um Effect chamado por `EffectCommand`: o Command coordena a intenção da UI; o retry continua sendo responsabilidade da operação.

## Ambientes locais e child Runtimes

`runWith`/`runExitWith` adicionam um `Module` somente a uma execução. `Runtime.fork` cria um ambiente de vida mais longa:

```dart
final checkout = await runtime.fork(checkoutModule, label: 'checkout');
try {
  await checkout.run(loadCheckout());
} finally {
  await checkout.close();
}
```

O child resolve localmente primeiro e faz fallback para o pai. Fechar o child não fecha o pai; fechar o pai coordena os children antes dos resources do root.

No Flutter, `BetterEffectFeatureScope` é o adapter que usa essa mesma capacidade para possuir um child Runtime durante a vida de um subtree.

Backends customizados precisam implementar `ResolverBackendOverlayFactory` para suportar overlays. O backend padrão já suporta.

## Observabilidade

`RuntimeObserver` recebe eventos síncronos de execução, resolução de serviço, aquisição/release, interruption, retry e cleanup failure. Erros lançados pelo observer são isolados e não substituem o outcome do Effect.

`EffectLocal.metadata` projeta valores selecionados para `RuntimeEventContext.localMetadata`. Prefira valores imutáveis e seguros para diagnóstico.

Commands Flutter podem fornecer `debugLabel`; essa label é propagada para a execução gerenciada do Runtime e pode ser correlacionada com a observabilidade do core.

## Testing

```dart
import 'package:better_effect/testing.dart';
```

A biblioteca de testing fornece `TestRuntime`, `ManualEffectClock`, `RecordingRuntimeObserver`, matchers/extractors de `Exit`, primitives determinísticas e o contrato para validar backends customizados.

`package:better_effect_flutter/testing.dart` reexporta esses helpers e adiciona utilitários específicos para Commands e widget tests.

## Quando não usar

Não adicione `Effect` por obrigação a lógica pura que já é clara como função Dart. O package também não substitui state management, HTTP client, banco, roteamento ou um framework de aplicação.

Se seu fluxo não precisa de falhas tipadas, DI contextual ou lifecycle de resources, `Future`/`ResultDart` diretamente podem ser a solução mais simples.

## Limitações que afetam design

- `Future` arbitrário não tem cancelamento físico geral;
- timeout/interruption encerram a ownership lógica antes da física quando necessário;
- defects não aparecem automaticamente no tipo `E`;
- retry com tempo/jitter exige serviços explícitos;
- overlays dependem da capacidade do backend de DI.
