`better_effect_analyzer` é o tooling oficial para projetos que usam `better_effect` e `better_effect_flutter`. Ele atua em duas escalas: o plugin do Dart Analysis Server encontra problemas locais durante a edição; o graph checker analisa a composição do projeto inteiro.

O package é tooling. Ele não participa do `Runtime`, não é necessário para executar um `Effect` e deve ser instalado como dependência de desenvolvimento quando a CLI/API de grafo for usada.

## Compatibilidade

```text
Package                 0.4.x
Dart                    >=3.10.0 <4.0.0
analysis_server_plugin  >=0.3.14 <0.3.18
analyzer                 ^12.1.0
```

Em aplicações Flutter, a compatibilidade real também depende da linha de `analyzer` fixada pelo SDK instalado. Não aumente esses constraints sem verificar o SDK.

## Duas camadas de análise

```text
Analysis Server plugin → arquivo/contexto resolvido, IDE, dart/flutter analyze
Graph checker           → roots, Modules, providers e dependências do projeto
```

O plugin não deve adivinhar qual `Module` representa o root completo de uma aplicação. O graph checker pode fazer essa pergunta explicitamente e construir uma visão global sem transformar cada diagnóstico do editor em uma análise de projeto inteiro.

## Instalação

Para usar a CLI ou a API pública de grafo:

```bash
dart pub add --dev better_effect_analyzer
```

Ative o plugin no `analysis_options.yaml` raiz:

```yaml
plugins:
  better_effect_analyzer:
    version: ^0.4.0
```

Reinicie o Dart Analysis Server depois de alterar a seção `plugins`.

## Warnings de correção

Ao ativar o plugin, a linha `0.4.x` registra sete warnings:

| Código | Detecta |
| --- | --- |
| `discarded_effect` | `Effect` lazy criado e descartado sem composição/execução |
| `discarded_effect_execution` | `EffectExecution` descartado sem observar ou retornar seu resultado |
| `runtime_started_without_close` | `Runtime` iniciado localmente sem ownership de fechamento verificável |
| `unawaited_effect_context_operation` | operação assíncrona de `EffectContext` ignorada sem `await`/return |
| `missing_binding_type_argument` | binding constructor-backed cujo contrato não fica claro |
| `incompatible_provider` | implementação que não satisfaz o contrato registrado |
| `duplicate_service_binding` | duas declarações com a mesma identidade de tipo + key |

Essas regras tratam problemas de correção, lifecycle e identidade de binding. Elas não dependem de a equipe adotar a arquitetura MVVM sugerida pelo package Flutter.

## Lints opt-in

As sete lints abaixo são conservadoras e precisam ser habilitadas explicitamente:

```yaml
plugins:
  better_effect_analyzer:
    version: ^0.4.0
    diagnostics:
      effect_command_not_owned: true
      closed_runtime_exposed: true
      module_root_not_complete: true
      repository_requests_repository: true
      viewmodel_requests_service: true
      widget_requests_business_dependency: true
      singleton_viewmodel: true
```

As regras `repository_requests_repository`, `viewmodel_requests_service`, `widget_requests_business_dependency` e `singleton_viewmodel` refletem uma direção arquitetural sugerida, não uma verdade universal:

```text
Widget → ViewModel → Repository / UseCase → Service / Client
```

Habilite-as somente quando essa fronteira fizer parte do contrato arquitetural do projeto.

As outras três ajudam a tornar ownership de Commands/Runtimes e roots completos mais explícitos durante migrações.

## Quick fixes

A versão atual registra fixes locais para casos em que a transformação é suficientemente segura, incluindo observar/retornar um `EffectExecution`, envolver um Runtime local em `try/finally`, registrar ownership de Command e converter um root visível para `Module.complete`.

Quando o ownership não pode ser inferido com confiança, o analyzer prefere diagnosticar a gerar arquitetura automaticamente.

## Graph checker

Rode a partir da raiz da aplicação:

```bash
dart run better_effect_analyzer
```

O checker indexa os `Module`s e as dependências descobertas e valida, entre outros pontos:

- serviços ausentes em roots completos;
- ciclos de dependência e de composição;
- `Module`s explicitamente selecionados que não existem;
- providers duplicados ou incompatíveis após composição/override;
- dependências entre resources incompatíveis com a ordem de startup;
- alguns problemas de ownership que possuem o mesmo código no plugin.

`Module.complete` é um marker estático para indicar que determinado root deve satisfazer todas as dependências alcançáveis. Ele não muda o comportamento do Runtime.

Ambientes criados com `Runtime.fork`, `BetterEffectFeatureScope`, `runWith`, `runExitWith` ou `executeWith` são tratados como overlays/scopes: o grafo local continua validando seus próprios providers, ciclos e resources, enquanto requisitos fornecidos pelo parent/root podem permanecer externos.

## Roots e inspeção

Selecione roots explicitamente:

```bash
dart run better_effect_analyzer \
  --module appModule \
  --module backgroundModule
```

Inclua arquivos de teste quando necessário:

```bash
dart run better_effect_analyzer --include-tests
```

Explique uma composição ou uma dependência:

```bash
dart run better_effect_analyzer --explain appModule
dart run better_effect_analyzer --why UserRepository
dart run better_effect_analyzer --unused
```

## Formatos e CI

Diagnósticos:

```bash
dart run better_effect_analyzer --format machine
dart run better_effect_analyzer --format json
dart run better_effect_analyzer --format sarif
```

Exportação do grafo:

```bash
dart run better_effect_analyzer --graph --format dot
dart run better_effect_analyzer --graph --format mermaid
```

`--output/-o` grava a saída em arquivo e `--schema-version` informa a versão pública do schema. Warnings são fatais por padrão na CLI; `--no-fatal-warnings` altera essa política quando isso for uma decisão explícita do pipeline.

## API pública para tooling

```dart
import 'package:better_effect_analyzer/better_effect_analyzer.dart';
```

A biblioteca exporta `BetterEffectGraphChecker`, `BetterEffectGraph`, os modelos versionados, queries e `BetterEffectGraphRenderer`. Use essa API quando uma ferramenta precisa consumir a análise sem parsear stdout da CLI.

## Limitações

A análise continua sendo estática. Factories executadas dinamicamente, composição opaca ou ownership que só existe em runtime podem não ser prováveis a partir do source. O analyzer evita transformar ausência de evidência estática em uma garantia que não pode verificar.

Uma lint arquitetural que não representa as regras do seu time deve ser desativada no mapa `diagnostics`; `ignore` local deve ser reservado para exceções pontuais.
