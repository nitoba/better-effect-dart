`better_effect` é uma família de packages para descrever operações de aplicação como `Effect<A, E>`, executar essas operações em um ambiente de dependências explícito e manter o ownership de recursos até a conclusão física do trabalho.

No Flutter, **esse modelo não é substituído por outro**. `better_effect_flutter` usa e reexporta o mesmo `Effect`, `Module`, `Runtime`, `Scope` e `Exit`; a camada Flutter acrescenta Commands, ownership no widget tree, ViewModels opcionais e widgets para renderizar ou reagir ao estado da execução.

A linha documentada atualmente é `0.4.x`.

## Dart e Flutter fazem parte do mesmo fluxo

```text
                     better_effect
┌──────────────────────────────────────────────────────────┐
│ Module → Runtime → Effect<A, E> → Exit<A, E>            │
│   │        │          │              │                   │
│   │        │          ├─ DI           ├─ Success         │
│   │        │          ├─ resources    ├─ Failure         │
│   │        │          ├─ retry        ├─ Defect          │
│   │        │          └─ concurrency  └─ Interrupted     │
└───────────────────────────┬──────────────────────────────┘
                            │
                            │ mesmo Runtime e mesmo Effect
                            ▼
                 better_effect_flutter
┌──────────────────────────────────────────────────────────┐
│ BetterEffectScope / Provider / Bootstrap                 │
│                    ↓                                     │
│               EffectCommands                             │
│                    ↓                                     │
│               EffectCommand                              │
│                    ↓                                     │
│            EffectCommandState                            │
│                    ↓                                     │
│ Builder / Listener / Consumer / Selector                 │
└──────────────────────────────────────────────────────────┘
```

Isso é importante porque APIs como `Effect.retry`, `Effect.forEach`, `Runtime.fork`, `runWith`, `EffectLocal`, `RuntimeObserver`, resources e testing continuam disponíveis em uma aplicação Flutter. O package Flutter adiciona a borda de apresentação; ele não cria um segundo runtime nem uma segunda semântica de erro.

Em uma aplicação Flutter, normalmente basta instalar `better_effect_flutter`: ele depende do core e reexporta sua API pública. O analyzer é uma `dev_dependency` independente.

## O problema que o projeto resolve

Em aplicações pequenas, `Future`, exceptions e um client acessado diretamente pelo widget podem ser suficientes. A dificuldade aparece quando as mesmas operações passam a precisar responder, de forma consistente, a perguntas como:

- essa condição é uma falha que o produto conhece ou um bug inesperado?
- qual implementação de um serviço esta execução deve usar?
- quem possui uma conexão, subscription ou transaction e quando ela fecha?
- o segundo toque deve ser ignorado, substituir a execução visível ou entrar em fila?
- uma interrupção da UI realmente cancelou o `Future` ou apenas deixou de esperar seu resultado?
- uma feature precisa de resources próprios sem promovê-los ao Runtime da aplicação?
- o grafo de dependências continua completo depois de uma refatoração?

A família separa essas responsabilidades sem esconder a relação entre elas:

```text
Module       descreve o ambiente
   ↓
Runtime      possui serviços, execuções e resources
   ↓
Effect<A, E> descreve a operação
   ↓
Exit<A, E>   preserva o outcome completo
   ↓
Command      executa o mesmo Effect na borda Flutter
   ↓
State        projeta o outcome para a View
```

## O primeiro princípio: nem todo erro é igual

`better_effect` trabalha com três categorias que não devem ser misturadas:

| Categoria | Exemplo | Representação |
| --- | --- | --- |
| sucesso | usuário carregado | `A` / `ExitSuccess` |
| falha esperada | credencial inválida, offline, regra de negócio | `E` / `ExitFailure` |
| defect | `Error`, dependência ausente, bug, falha de cleanup | `ExitDefect` ou exceção na API baseada em `Result` |

Interrupção é um quarto outcome em `Exit`: `ExitInterrupted`.

No Flutter, `EffectCommandState<A, E>` preserva essa mesma separação com estados próprios para success, failure, defect e interruption. O Command não reduz o modelo a `loading + error`.

## O que existe na camada Flutter

A integração Flutter é dividida por responsabilidade:

| Responsabilidade | APIs |
| --- | --- |
| iniciar a aplicação | `runBetterEffectApp`, `BetterEffectBootstrap` |
| publicar um Runtime existente | `BetterEffectProvider`, `BetterEffectProvider.value`, `BetterEffectScope` |
| criar ambiente por feature | `BetterEffectFeatureScope` |
| criar Commands | `EffectCommands`, `EffectCommand0`, `EffectCommand` |
| possuir Commands | `EffectViewModel`, `EffectCommandOwner`, `EffectViewModelBuilder` |
| renderizar estado | `EffectCommandBuilder` |
| executar side effects one-shot | `EffectCommandListener` |
| combinar render + listener | `EffectCommandConsumer` |
| reduzir rebuilds | `EffectCommandSelector`, `EffectCommandSelector.snapshot` |
| acessar o scope | `context.effectCommands`, `watchEffectCommands`, `effectRuntime`, `runEffect`, `runEffectExit`, `readEffectService` |
| testar widgets | `BetterEffectTestApp` e probes de `package:better_effect_flutter/testing.dart` |

A página [`better_effect_flutter`](/docs/packages/better_effect_flutter) explica essa superfície inteira e o guia [Flutter: integração completa](/docs/guides/flutter-mvvm) mostra como as peças se encaixam em um fluxo real.

## O que a biblioteca garante — e o que ela não promete

As garantias estáveis de lifecycle e outcomes são versionadas em [`SEMANTICS.md`](https://github.com/nitoba/better-effect-dart/blob/main/SEMANTICS.md) e verificadas pelo package interno de conformance. Consulte o [contrato semântico](/docs/semantics) quando uma decisão depender de precedence de cleanup, interruption, retry, concorrência ou ownership.

Algumas limitações são intencionais:

- Dart não oferece cancelamento físico geral de qualquer `Future`; timeout e interruption podem encerrar a espera lógica antes do trabalho físico;
- `Effect.tryAsync` captura `Exception`, não todo objeto lançado; `tryAll` é a fronteira explícita para capturar tudo;
- `EffectClock` e `EffectRandom` não são instalados implicitamente;
- `better_effect_flutter` não substitui um state manager ou roteador;
- as lints arquiteturais do analyzer são opt-in e não são tratadas como verdades universais.

## Versão, compatibilidade e migração

Os três packages do monorepo estão na linha `0.4.x`, mas são publicados de forma independente. Antes de copiar um exemplo, confirme a versão realmente instalada no `pubspec.lock`.

Mudanças relevantes por release ficam nos `CHANGELOG.md` de cada package. Alterações de semântica estável também precisam de uma entrada no [ledger de migrações semânticas](https://github.com/nitoba/better-effect-dart/blob/main/docs/semantic-migrations.md).

APIs depreciadas devem ser tratadas como caminho de migração, não como recomendação para código novo. No Flutter, por exemplo, `BetterEffectLifecyclePolicy` substitui parâmetros legados de fechamento; `CommandPolicy` é a API preferida quando a coordenação precisa ir além do shorthand `EffectCommandConcurrency`.
